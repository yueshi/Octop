一、结论先行

Octop 已具备实现「主动工作团队」约 60% 的地基：主持人调度角色、异步派工/回叫、房间上墙、 HITL 审批闭环、cron 无人值守运行、轻应用与通知 WS 均已存在。核心缺口是五个： 任务无实体、主持人不能主动开工、无人值守遇审批即失败、无显式求助通道、看板缺基础设施。

方案 = 给团队加「目标/任务实体 + 驱动循环 + 持久化 HITL + 原生看板」，四个能力各自独立可交付； 轻应用作为 P2 阶段的看板自建/组合路径。

二、目标需求

需要一个能主动工作的团队：设置整体目标后，任务由主持人驱动产生、选择、分配、执行； 必要时向团队创建人提出帮助或操作要求；根据任务执行状态提供必要的进度汇报和方向调整决策； 团队对外提供一个看板（可基于轻应用功能自主搭建或组合）； 创建人可通过对话和看板随时关注。

四、五大核心缺口

  1. 目标/任务不是实体 —— 团队里「任务」只是消息文本，无持久化、无状态机，重启即丢 （infra/agents/teams/service.py:26-38 主持人仅 5 个工具，无任何任务工具）。
  2. 主持人不能主动开工 —— team host 不注册 cron 工具（工具装配处 if not team_host 直接跳过，infra/agents/manager.py:3782-3786）；成员虽可自挂 cron，但结果只投递到 job 绑定 session 的渠道、不经房间编排回流——团队实质只能靠用户消息驱动。
  3. 无人值守遇审批直接失败 —— cron 运行遇 hitl_required 判失败而非挂起 （infra/cron/delivery.py:166-169）；HITL pending 纯内存、30 分钟 TTL （infra/gateway/hitl/store.py:13），长任务等不起。
  4. 无「向创建人求助」显式通道 —— HITL 只覆盖工具审批；主动推送只有文本 + toast （infra/gateway/gateway.py:507-522），不会把待决策卡片定向推给创建人并等待其决定。
  5. 看板缺基础设施 —— 轻应用只有「读 + 追加」（无行 id、无行级更新、无视图层）；dashboard 无拖拽依赖。

七、分模块详细设计

7.1 数据模型（迁移号按 §11-B9 定，SQLite/pg 成对）

-- 遵循资源表规范：公开 string id + 整数 PK；team_id 引用 agents.agent_id 字符串 team_goals id, goal_id(公开 string), team_id(→agents.agent_id), title, description, status(planning|active|paused|done|archived), success_criteria, created_by, created_at, updated_at team_tasks id, task_id(公开 string), team_id, goal_id(→team_goals.goal_id), title, spec(任务说明书), assignee(成员 id), status(proposed|assigned|running|blocked|needs_input| review|done|failed|cancelled), priority, result_summary, blocked_reason, version(乐观锁), created_at, updated_at, due_at hitl_pending id, session_key, thread_id, kind(tool_approval|question), payload(JSON), created_by_agent, task_id(可空；ask_creator 去重键), status(pending|approved|rejected|expired), expires_at, resolved_by, resolved_at, resume_token
  • 团队是 agents.kind='team' 的行，team_id 引用 agent_id 字符串； 两表各带公开 string id（goal_id / task_id）， goal_id 引用父表字符串 id（AGENTS.md §7 资源表约定， PATCH …/tasks/{task_id} 与 hitl_pending.task_id 均依赖后者）。
  • hitl_pending 是对现有内存 HitlPendingStore（store.py:13,38-110）的持久化落点： 写入时同步落库，重启时 boot 恢复未过期条目、将过期未决行置 expired， TTL 可按 job 配置（无人值守长任务需要 >30min）；持久化状态四态与内存 store （store.py:11）对齐，不压缩成两态。
  • 任务子表不进轻应用 CSV——需要行级并发更新与乐观锁，这正是轻应用当前明确缺的 （service.py:1039-1090 整文件重写）。
  • v3 并发控制：team_tasks 有两个写方——主持人工具（驱动循环/回叫） 与创建人看板拖拽（PATCH）。加 version 列做 compare-and-swap， 冲突返回 409；PATCH 的状态变更由服务端校验状态机合法流转， 不信任前端任意置 done（→ §7.6）。
  • v3 求助去重：hitl_pending.task_id 非空时， 同任务已存在 pending 行则拒绝重复 interrupt——防 blocked 任务 每个驱动周期重复发通知（→ §7.4）。

7.2 主持人驱动闭环（核心）

  1. 工具扩展：六个薄包装工具 goal_set / task_create / task_update / task_list / report_progress / ask_creator （后两者见 7.4 / 7.5）：调 team repo，写 team_goals / team_tasks； 向房间发结构化事件消息时复用 _persist_room_assistant 上墙路径 （team_manager.py:1317），事件消息打标记、走投影层渲染规则（折叠/合并）， 避免与 wake 帧同病刷屏（→ §7.3 隐形 wake）。 v3 P1 已落地（4/6）：前四个工具已实现，挂载方式改为 build_team_board_tools()（infra/agents/teams/board_tools.py）构建、 经理装配时按 team_host 注入 HarnessAgentConfig.tools （manager.py _agent_runtime_bundle），不动 HOST_TOOLS_ALLOWED（规避 host_tools_disabled 联动）； report_progress 顺延 P2/P3（依赖 notify/gateway 通道）、 ask_creator 顺延 P3；房间结构化事件消息随 P2 驱动循环落地—— P1 阶段工具调用均发生在主持人可见回合内，回复本身即上墙，无刷屏问题。
  2. 驱动循环 prompt：目标设定（或 cron 唤醒）时注入固定 wake prompt—— 「读取未完成任务，继续推进/派工/汇报；有阻塞则 ask_creator」。主持人 LLM 负责产生（拆解目标）、 选择（排优先级）、分配（ask_agent 派工）、执行跟踪（回叫后 task_update）。
  3. 状态机：成员回叫（on_reply，team_manager.py:319-363）→ 主持人 compose_followup 总结 → task_update(status=done/failed/blocked)； needs_input 状态与 ask_creator 联动。 v2 补两条流转： ①派工失败重试——async ask_agent 走 inbox 排队，成员 busy 会等锁而非拒派 （TEAM_MEMBER_BUSY 仅用于删除守卫，service.py:239-250）； 派工失败发生在成员未运行/不存在等场景，经 on_reply 报错回房， 任务由驱动循环下轮重试或改派，主持人不另开新任务； ②stale 回收——inbox 重启丢在途任务是团队第一版明示的非目标 （docs/expert-teams.md:156-162），自治循环将其放大：驱动循环每次唤醒检查 running 任务，若进程内在途锁（jobs.py TeamJobTracker）已丢失 （重启后必然丢失）则改判 failed（注明 stale）或回退 proposed 由下轮重派——不判 needs_input（该状态语义是「待创建人输入」， stale 场景并无待决事项），杜绝永久卡死。
  4. 验证：单元测状态机与工具参数；集成测「设目标 → 房间内主持人产 2-3 个任务并派工 → 成员回叫 → 任务关单」；v2 追加：派工失败重试、重启后 stale 任务回收两个用例。

7.3 主动唤醒（cron 解禁，受控）

  • 改 infra/agents/manager.py:3782-3786（host 现状不注册 cron 工具）：为 host 新注册受限的 cron 工具子集——只能创建 task_type=agent、 session_key=团队房间线程、prompt 固定为驱动循环模板的 job； 且限频（如 interval 下限 15 分钟）防风暴。
  • 投递路径现成：cron → delivery.py → agent_manager.stream → 房间线程 → on_reply 上墙；dashboard 收到 toast（gateway.py:507-522）。
  • 必须同步解决： delivery.py:166-169 的「遇 hitl_required 即失败」→ 改为「任务挂起 + 落 hitl_pending + 通知创建人」（见 7.4）；否则周期驱动第一次遇到审批就断。 该项在 §八 属 P3，但必须不晚于 P2 合入——它是 P2 驱动循环的前置。

v2 反思后补充四项防失控机制：

  • 隐形 wake：cron 的 task_type=agent prompt 会作为消息进入房间并上墙—— 15 分钟一次会把创建人的房间刷满机械消息。wake 帧必须带标记并在投影层 （history/projection.py）过滤渲染，仅在有实质产出（新任务/状态变更/汇报） 时转播到房间。独立影子 session 不可选——与「驱动 job 必须 fresh_thread=false 同房间续聊」（下文）冲突，不采用。
  • 预算闸门：只对 cron 限频不够，单次 wake 内部也要限——每次唤醒最多派 N 个任务 （建议 N≤3）、单团队最大 open tasks（建议 ≤10）、（可选）token 消耗帽， 防「自我定时执行的 LLM」在目标误解析后无限产任务。
  • kill switch：现状取消只断主持人当前 stream，inbox 里排队/在跑的成员任务不取消 （docs/expert-teams.md 装配节）。自治模式需要完整停止语义： 停用驱动 cron + 清空 inbox + open tasks 置 cancelled + 关联 pending 失效。
  • 生命周期级联：删除团队时级联停用其驱动 cron job、关闭未完任务、 失效 hitl_pending 行——host 自建的 job 若不处理，团队删除后会变成孤儿定时炸弹。

v3 第二轮反思补充：

  • host 未运行时的驱动行为：成员「last_state 非 running 则调用失败」是现状； team host 自身被停止后，驱动 cron 触发 agent_manager.stream 也会失败。需定义： 自动拉起 host（推荐，保持自治语义）或跳过并记录 last_status。 同时驱动 job 必须 fresh_thread=false（同房间续聊，主持人才能读到任务历史）。
  • 存量团队迁移：种子（SOUL.md / AGENTS.md / manifest）只在创建时写入。自治能力的新指导 应放进运行时拼装的 host_system_prompt（team_manager.py:103-114） 或 wake prompt，而非依赖工作区种子——否则只对新建团队生效，存量团队无感。
  • 提示注入防线：目标文本是创建人写的可控；但 agently 邮件等外部内容若流入 wake 上下文，恶意邮件正文即可指挥自治团队。驱动循环 prompt 必须把外部内容当数据不当指令， 且外部事件触发器默认不进自治循环（仅白名单触发器可注册为驱动源）。
  • 成本配额：15 分钟一轮 × 多成员的 token 消耗，应接 usage_log 做 每团队/每用户周期预算检查，超限自动暂停驱动循环——这是累计账单闸门， 与 §7.3 单轮预算闸门互补。
  • 观测性：接 infra/metrics.py 计数器（wake 执行/失败、任务流转、HITL 超时）， 否则线上「团队卡死」无法事后归因。

7.4 求助/审批闭环（HITL 持久化 + 定向推送）

  1. 持久化：gateway/hitl/store.py 读写改为内存 cache + hitl_pending 表双写， boot 时恢复。harness 的 interrupt checkpoint 本就在 workspace sessions 下 （docs/architecture.md §4），重启后 resume 链路可验证。
  2. cron/团队遇 HITL：不判失败，创建 pending 行 → 通过 notifications WS （chat/notify_ws.py:26，按 user 注册）定向推创建人： {"type": "approval_required", team_id, task_id, pending_id, deep_link} ——信封沿用现有 type 字段约定（与 dashboard_push、 team.task.updated 一致），前端只对接一种形状。
  3. ask_creator 工具：本质是 ask_user_question 类型的 HITL interrupt， 语义化包装（问题 + 选项 + 关联 task_id）；复用 coordinator.py:325-339 的 respond 决策类型。主持人可在成员 blocked 时转达求助。 v3 去重：同 task 已有 pending 行则拒绝重复 interrupt， 通知合并计数（→ §7.1）。
  4. 回应入口：房间审批卡（已有，team_manager.py:381-449）、 看板「待我决策」区、创建人 DM 回复——三个入口都落既有 POST /chat/hitl/resume。
  5. cron 写限制（delivery.py:149 整体禁写）：改为 「默认禁写 + 该 session 存在已批准的写审批则放行」，与批准模型对齐。
v3 验证门结论（已读码核销，2026-10-25）： ① write_scope(allowed=False) 只挡 agently 邮件写工具——作用域是 agently_cli.py:106-117 的 ContextVar，仅 _WRITES 五个邮件写工具消费； 内部工具/DB 写不受影响，驱动循环在 cron 上下文可正常调 task_update（C11 核销）。 ② ask_user_question 的工具函数体无条件返回 HEADLESS_FALLBACK （ask_user.py:126）——真正拦截在图的 interrupt_on 配置， 开关是静态 agent 配置（_ask_user_active，harness agent.py:1392-1400）， 与运行上下文无关；cron 与 dashboard 走同一 agent_manager.stream、同一份配置， delivery.py:166-169 存在 hitl_required 分支本身就证明 cron 运行会 interrupt （C12 核销）。实现要求：ask_creator 必须像 ASK_USER_TOOL_NAME 一样显式注册进 interrupt_on（仿 agent.py:1413 的 respond-only 配置）， 否则才会真的静默自答。 另：C13 已于 P3 落地时验证（2026-10-25）：host 停在 HITL 暂停时，成员 on_reply 回叫照常送达房间且 pending 暂停不被破坏（test_member_reply_survives_host_hitl_pause）。

7.5 进度汇报与方向调整

  • 事件流：task_* / goal_* 工具每次写库同时经 WS hub 广播 team.task.updated 事件（看板增量刷新）；activity feed 直接读任务表 updated_at 排序，或复用 audit_log。
  • 汇报：report_progress 工具（主持人）把结构化摘要推到创建人 dashboard DM 线程 （dashboard_key，threads.py:87-92）；里程碑完成也可由驱动循环 cron 自然覆盖。
  • 方向调整：创建人在房间/看板评论 → 下轮驱动循环主持人消化（零新代码，聊天即输入通道）。

7.6 看板

十、风险提示

harness 侧联动 —— ask_agent / inbox / wire_host_dispatch 在 octop-harness 库内（octop_harness/teams/tools.py:161-250）， 工具白名单与 interrupt 语义若有出入需要跨库发版协调。
重启恢复是 P3 最大的不确定点：langgraph interrupt 的 checkpoint 恢复在真实长任务上需要专门验证 （本地 SQLite 快；「远程后端 workspace 的 sessions 路径已在本地，风险可控」目前是断言， 已列入附录 C14 待验证）。
解禁 cron 的安全面：host 可创建 job 等于代码可自我定时执行， 限频 + 模板锁定 + 沿用仅-owner 校验（cron/tools.py:100-267）三重约束缺一不可。
v2 多租户饿死：派工走共享成员时，「同一成员串行」的 inbox 并发模型意味着某创建人的团队长任务会饿死该共享专家的其他用户。 需要成员忙碌配额，或自治派工优先使用团队独占成员。
