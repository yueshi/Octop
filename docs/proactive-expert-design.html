一、结论摘要（问题 A）

判定：有条件可行，且实施成本低于团队版。
单专家自治的无人值守链路、任务底座、HITL 机制、主动先例四项关键地基全部现成或已由团队版 P1 落地； 硬前置只有三个，且全部与团队版 P2/P3 共享同一批改动。

依据（均有代码实据）：

  1. 无人值守执行链路对单专家是现成的。普通专家默认拥有全部 6 个 cronjob_* 自注册工具 （cron 工具仅对 team host 跳过，infra/agents/manager.py:3782-3786）；cron task_type=agent 的完整执行链（session 锁内 stream、usage 记账 source="cron"、 结果推送）与 kind 无关（infra/cron/delivery.py:134-192）。 团队版 P2 要「解禁」的东西，单专家现状就有。
  2. 任务/看板底座已落地且 repo 层零 kind 过滤。team_goals/team_tasks 外键是 REFERENCES agents(agent_id)，无 kind 约束（infra/db/migrations/022_light_apps.sql:98-133）； assignee 同样引用 agents(agent_id)——专家自治任务 assignee=self 与团队派工 assignee=成员 在同一张表语义天然统一。repo、状态机（task_state.py）、 工具实现（board_tools._tool_ctx() agent 无关，board_tools.py:47-60）全部可直接复用。 kind 过滤只存在两处薄层：API 路由（teams.py:70-72）与工具挂载条件（manager.py:3833）。
  3. 单专家比团队少一整层分布式复杂度。无派工/inbox/房间编排/回叫——「读任务→领取→执行→回写→汇报」 在同一个 ReAct 回合内闭环；docs/expert-teams.md:156-162 明示的「inbox 重启丢在途任务」 非目标对单专家自治基本不构成威胁（无跨 agent 在途状态）。
  4. 单 agent 主动行为已有先例。主动关怀具备完整 per-agent 调度器、免打扰窗、随机频控、去重与推送链路 （infra/proactive/scheduler.py:44-108,274、infra/proactive/service.py:117-263）， 其策略参数可直接泛化为自治运行策略。

条件（三个硬前置，全部与团队版 P2/P3 共享）：

C1 无人值守遇审批挂起——cron 运行遇 hitl_required 现状直接判失败 （delivery.py:166-169），必须改为挂起+通知（团队版 P3 同批改动）。
C2 预算与闸门——usage_log 可按 agent/user 聚合但无任何预算检查代码 （infra/db/repos/usage.py:250-498，已验证），失控防护必须新建。
C3 底座通用化——工具挂载条件放宽 + agent 通用 API 路由 + i18n 专家变体（均为小改，见 §五 E1）。

不满足 C1/C2 就上线自治 = 团队版 v2 反思 A1–A7 风险的单专家复刻；满足后，单专家自治是团队自动驾驶的 n=1 特例，应共用全部底座（详见 §七）。

本次补充核验（2026-10-25）：U1/U2/U4 已验证（附证据），U3 已验证并修正为 「串行排队延迟」风险项，U5 仍未验证。详见 §九。

五、关键差距与设计调整（问题 D）

5.1 MVP（最小可用）

E1 底座通用化（改动最小的一档）

  • 数据：零迁移（三表复用；不推荐 SQL 视图别名增加维护面）。 agents 行新增开关 autonomy_enabled（默认关）→ 折叠进未发布的 022 （团队版 B9 结论：022 未进 main/develop）。
  • 工具挂载：manager.py:3833 条件 if team_host: → if team_host or autonomy_enabled；挂同一 build_team_board_tools()。 assignee 对单专家恒为自身 agent_id（工具内校验：expert 上下文不允许 assignee 指向他人， 防自治专家把任务甩给别的 agent 而无派工语义）。
  • API：新增 api/routers/agent_work.py—— GET/POST /api/agents/{agent_id}/goals、GET /api/agents/{agent_id}/tasks、 PATCH /api/agents/{agent_id}/tasks/{task_id}（鉴权 assert_agent_owner + admin bypass， 沿用 P1 的 CAS 409 + 状态机 400 校验）。/teams/* 路由保留不动。
  • i18n：teams.autopilot_briefing 增专家变体键（en/zh 对齐，跑 tests/unit/i18n）——强调「自产自执行自回写、blocked 时 ask_owner」。
  • 注入点：仿 append_light_app_system_prompt（manager.py:3994-3998） 按 source=autopilot 追加自治指导，不依赖种子。

E2 驱动循环（与团队 P2 同一批改动，共享代码）

# wake 模板（cron_jobs.meta.autopilot=true 时锁定） 约束 session_key=dashboard_key · fresh_thread=false · interval ≥ 30min prompt 读取 open tasks → 领取一条（置 running）→ 执行（工具循环/ 必要时 sync ask_agent）→ task_update 关单 → 汇报； blocked 则 ask_owner 闸门 单 wake 领取 ≤2 · open tasks ≤8 · usage 周期配额超限自动暂停
  • 触发：专家自建 cron（能力已有），服务端约束见上；date 一次性触发（「明早 9 点做 X」）天然支持，无需新代码。
  • 隐形 wake：投影层过滤标记帧（与团队共享同一实现）。
  • kill switch：停 meta.autopilot job + open tasks 置 cancelled + 关联 pending 失效。
  • U3 核验后新增 待定项——wake 与用户对话的串行排队：wake 与用户 同会话入站轮次被 session 锁串行互斥（delivery.py:69-88 包 run_in_session）， wake 是完整 ReAct 工具循环，会给同时在线的用户带来可感知排队延迟。E2 设计须把以下列为待定项： ① wake 单轮时长上限（超时熔断，避免长时间占锁）； ② 抢占策略（候选：唤醒时段避开用户活跃时段 / wake 轮次超时熔断 / 用户消息优先抢占—— run_in_session 现状是先到先得，需评估在锁队列中给用户入站轮次插队）； ③ 保守默认：active_hours 限窗 + 用户活跃时段不排 wake。

E3 求助闭环（与团队 P3 合并交付，单专家可作试点）

  • hitl_pending 持久化：store 双写 + boot 恢复（表已建）。
  • delivery.py:166-169：遇 HITL → 建 pending 行 + notifications WS 定向推 owner （chat/notify_ws.py:26）+ deep_link 到专家会话/看板卡。
  • ask_owner 工具：ask_user_question 包装 + 显式注册 interrupt_on （团队版 §7.4 v3 callout 的实现要求）+ hitl_pending.task_id 去重（同任务单活跃 pending）。
MVP 验证标准：单测（状态机流转、挂载条件、meta.autopilot 约束、预算闸门）； 集成（设目标 → wake 触发 → 产任务并执行关单 → owner 收汇报；wake 中触发工具审批 → owner 批准 → 续跑，含重启恢复）； make all 全绿；跨平台约定（OCTOP_HOME monkeypatch、Path 断言）。

5.2 完整形态

  • E4 看板：团队 P4 页面按 agent 通用渲染（kind 徽标区分 team/expert，路由统一 /agents/{agent_id}/board，团队路径做别名）；同一 CAS/PATCH 路径；服务器时区渲染（D19 继承）。
  • E5 运行策略：泛化 proactive_care_config 为 autonomy_policy （active_hours/min_interval/quiet/预算）——care 与 autonomy 共用策略存储与求值 （scheduler.py:44-108 触发算法直接改造复用）；事件触发器白名单 + 注入防线（D21 继承）。
  • E6 长任务与组合：spawn subagent 执行长任务（task 工具 + SubagentCatalog 安装流）+ 子任务 stale 回收； MiniApp 投影（团队 P5 共用：team_tasks 数据源）； infra/metrics.py 观测（wake 执行/失败/任务流转/HITL 超时）。

5.3 单专家特有的状态机补充

  • assigned 语义微调：推荐保留为「计划内未开始」（少改状态机）；wake 领取直接 running。
  • review：单专家无主持人审，默认「自审 + 可选 owner 验收开关」（团队版 A5 结论的 expert 版）； success_criteria 写入 goal 作为 wake 自检依据。

六、风险与人工闸门（问题 E）

风险单专家场景的形态缓解 / 闸门
失控循环目标误解析 → 无限产任务/自催 预算闸门（E2）；C2 是硬前置
误操作面大专家有全量工具（邮件/MCP/文件写）vs 主持人仅 5 工具——自治风险高于团队版 ① cron write_scope 禁写维持 + 批准放行（§7.4-⑤）；② MANDATORY_HITL_TOOLS 扩展 （现有 {"app_delete"}，hitl_session.py:22，自治上下文可叠加高风险写工具）； ③ 线程 bypass 不覆盖 mandatory（hitl_session.py:255 已保证）
提示注入外部内容（agently 邮件、connector 同步）流入 wake 上下文即可指挥专家 外部内容 data-not-instruction；外部触发器默认不进自治循环（D21 继承）
成本wake = 完整 ReAct 工具循环，比 care push（过程式 ≤200 字）贵 1–2 个量级；但无多成员放大 active_hours 默认窗 + interval 下限 + usage 配额（E5）
自产自审无独立审核环节，质量风险内化 review 状态 + owner 验收开关（默认开）；success_criteria 作 wake 自检依据
跨 agent 干扰sync ask_agent 可调同 user 全部 agent——自治 wake 里调他 agent 可能长阻塞对方会话 自治上下文限制 ask_agent 目标白名单或默认禁用；MVP 不宣传该路径
U3 已验证 wake 排队延迟 cron wake 与用户同会话串行（delivery.py:69-88 包 run_in_session）， 长 ReAct 轮次会阻塞用户消息（或被用户消息阻塞） active_hours 限窗避开用户活跃时段；wake 单轮时长上限 + 超时熔断； 评估用户消息优先抢占（→ §五 E2 待定项）
累计账单usage_log 有明细无检查E2/E5 周期配额闸门
应保留的人工闸门（不可 bypass）：ask_owner 求助、工具审批（mandatory 清单）、kill switch、 write_scope 禁写默认、active hours 默认窗。 自治专家的「自由度」必须小于对话态专家——无人值守是更严的上下文，不是更松的。

分工定位：团队 host 保留「调度/汇总」职能（goal 拆解、派工、compose_followup）； 单专家自治不做调度（不引入派工队列），只做「自我管理」（目标→任务→执行→汇报）。 两者共存于同一 user 时互不干扰：专家自治任务与团队任务共享一张看板（owner 视角全量可见，assignee 徽标区分来源）。
