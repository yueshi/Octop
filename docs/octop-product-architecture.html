01 · 30 秒读懂

智总管不是“另一个聊天机器人”，而是可自托管的 AI 工作平台

智总管把“人和 AI 对话”升级为“每个用户拥有自己的 Agent，团队拥有可编排的专家，业务结果以应用、看板、文档和交付物的形式落地”。所有状态默认放在自己的机器上，模型、存储、通道和连接器都可以替换。

销售产品研发
◎

对个人：一个记得你、能动手的专属助理

专属 Agent、长期记忆、知识库、浏览器、终端、定时任务和 IM 触达。它不只回答问题，还能查资料、整理文件、写周报、跑自动化。

◫

对团队：多用户、多专家、可编排的数字同事

每个成员有自己的 Agent；专家可共享；团队由主持人调度成员；目标、任务、审批、预算、交付物在看板上闭环。

↗

对企业：可私有化、可接业务系统、可交付应用

JWT / SSO / LDAP、ACL、审批、PII 脱敏、审计、TLS、备份；连接器与 MCP 接入现有系统；MiniApp 把数据变成可用的看板与台账。

一句话理解

智总管 = 多用户 Agent 运行时 + IM 网关 + 专家/团队编排 + 连接器/知识库 + 自动化/事件 + MiniApp 交付面 + 自托管运维。它用一个 Python 进程把这些能力装在一起，除 LLM provider 外不依赖外部队列或必需服务。

适合谁

  • 10–500 人的团队或部门，日常协作在飞书 / 钉钉 / 企微 / 微信 / Telegram / Discord
  • 希望数据留在自己机器、内网或自有云上的企业
  • 有大量文档、制度、产品资料，需要“能引用、能追溯”的知识助手
  • 需要多个角色 Agent 分工，而不是一个通用聊天窗口
  • 有运营台账、客户跟进、报表看板等“最后一公里”交付需求
  • 有研发/运维团队，希望把 ACP、终端、浏览器、定时任务接进 AI

不适合谁

  • 需要多租户 SaaS、跨地域高可用、分布式集群的超大规模场景
  • 需要严格确定性的 BPM / 工作流引擎，且不能接受 Agent 的不确定性
  • 没有 LLM provider、没有可运行服务的机器，且不愿做任何运维
  • 希望“完全无人值守、零人工审批”的高风险业务
  • 只需要一个开箱即用的垂直行业 SaaS，不需要定制与集成
02 · 定位与边界

它的位置：Agent 交付物的着陆场，而不是业务数据库

智总管的强项是“把 AI 能力组装成一个可运行、可协作、可交付的平台”。理解它“是什么”和“不是什么”，比记住功能列表更重要。

销售产品

它是什么

  • 多用户 Agent 平台：每个用户可有多个 Agent，各自拥有工作区、模型、通道、定时任务与记忆。
  • 统一入口：Web、CLI、IM、HTTP/WebSocket API 共用同一套 Agent 运行时。
  • 可编排的专家团队：专家库、人格、技能、子代理、团队主持人 + 成员。
  • 可接入外部世界：30 个连接器、OAuth、MCP、浏览器、终端、远程桌面、ACP。
  • 可交付的业务面：知识库问答、定时任务、外部事件、MiniApp 台账/看板/公开链接。
  • 可自托管的运维形态：安装向导、TLS、服务化、备份、更新、i18n、API 文档。

它不是什么

  • 不是纯云端 SaaS：默认自托管，数据和密钥在本地；也不是开箱即用的多租户云服务。
  • 不是 RPA / BPM 工作流引擎：Agent 擅长灵活判断与工具调用，不擅长严格确定性的流程编排。
  • 不是分布式集群：单进程、单节点设计；跨节点请用“每节点一个智总管 + 外部协调层”。
  • 不是业务数据库的权威源：MiniApp 是投影层；任务实体、审计、审批仍落原生表。
  • 不是零配置的行业 SaaS：需要配置模型、通道、连接器、权限和运维。
产品经理提示

对外表达时，建议把智总管描述为“可自托管的 AI 工作平台”，而不是“万能 Agent”或“企业级分布式 AI 中台”。前者准确且可验证；后者会带来多租户、分布式、SLA 等不必要的高预期。

典型买家核心诉求最匹配的能力建议切入方式
中小企业 / 部门负责人团队提效、知识沉淀、IM 内可用多用户 + 专家 + IM + 知识库 + 定时任务从一个 IM 群 + 一个知识库 POC 开始
企业 IT / 数字化负责人私有化、SSO、权限、审计、可运维JWT / OIDC / LDAP、ACL、审计、TLS、备份、PostgreSQL先做内网单节点，验证模型与权限，再扩团队
业务运营 / 销售负责人客户跟进、台账、报表、提醒连接器 + 记忆 + Cron + MiniApp + 公开链接用 Excel 台账 → 看板的 10 分钟演示切入
研发 / 运维负责人排障、自动化、代码与浏览器操作ACP + 终端 + 浏览器 + 事件 + Cron从“只读排障助手”开始，逐步开放写操作
家庭 / 个人极客一个长期陪伴、能动手的助理个人 Agent + 记忆 + IM + 浏览器 + 知识库Desktop / Docker 一键部署，先个人使用
03 · 功能全景

八块能力，拼成一个完整的 AI 工作平台

下面按“用户能感知到的能力域”组织，而不是按代码目录。每个域都标注了成熟度，方便销售判断能不能承诺、产品判断先做什么、研发判断改哪里。

销售产品研发
◉

1. 多用户与多入口

  • Web Dashboard：聊天、专家、团队、连接器、通道、Cron、知识库、插件、设置、MiniApp 工作台、ACP、远程桌面。
  • CLI：octop run、init、service、chats、provider、cron、backup、skills、plugin、acp 等。
  • 10 个 IM / 消息通道：飞书、钉钉、QQ、微信、企业微信、Telegram、Discord、MQTT、小艺、元宝。
  • API：HTTP + WebSocket；流式聊天走 WS，部分 HITL/流式接口用 SSE；/api/docs 可在配置中开启。
  • 桌面端：Windows / macOS / Linux；FnOS NAS 包；移动端在内部测试阶段。
  • 认证与权限：JWT、管理员、邀请码、OIDC SSO、LDAP、验证码、登录锁定、资源级 ACL。
✦

2. Agent 与专家

  • 每用户多个 Agent：独立工作区、模型 provider、通道、Cron、记忆。
  • 专家库：20+ 内置模板，覆盖通用助理、工程、设计、运营、财务、法务、医疗学习、腾讯云、微信运营等。
  • 人格：16 型 MBTI 模板 + 自定义系统提示 + SOUL.md，让角色稳定。
  • 技能 / 子代理：技能包、SkillHub、共享资源池、子代理派生。
  • 工具：60+ 内置工具位（文件、搜索、浏览器、终端、记忆、Cron、知识库、MiniApp、移动端等），外加 MCP / 插件工具。
  • 模型：OpenAI 兼容、DashScope、Ollama 及多种预设；provider 健康检查与熔断。
◇

3. 团队与自治

  • 专家团队：主持人 + 至少 2 名成员；主持人调度，成员独立工作区；群聊上墙、成员侧栏、异步派工。
  • 目标 / 任务 / 看板：目标、9 态任务机、依赖、优先级、截止、CAS 更新、交付物。
  • Autopilot（Beta）：runtime / events / decisions / waits / sweeper；启动、暂停、恢复、完成、全停。
  • 预算与审批：团队/数字员工预算、HITL 持久化、ask_creator、收件箱。
  • 数字员工（Beta）：单专家自治，复用目标/任务底座，自己执行、自己回写。
  • 共享与桥接：专家分享、知识库分享、跨实例 Bridge。
▤

4. 知识与记忆

  • 知识库：文档导入、切分、向量检索、引用、部署内共享。
  • 本地 embedding：可选 ONNX 模型，离线可用；大文档后台索引。
  • 长期记忆：octop-memory，分层召回 + 全文检索；记忆随工作区迁移。
  • 上下文效率：文件系统 offload、分层提示词、记忆压缩、memory slim。
  • 历史：threads / messages 投影、执行轨迹、可选分段归档。
⇄

5. 连接器与扩展

  • 30 个内置连接器：腾讯文档、腾讯会议、腾讯乐享、微云、微信读书、Notion、Obsidian、语雀、飞书/企微/钉钉 CLI、企查查、滴滴、有道、Dify、WeKnora、HTTP 取数等。
  • OAuth + MCP：OAuth 应用、MCP 网关、自定义 MCP server、只读工具校验。
  • 插件：27 个内置插件 + 第三方插件；工具、UI 卡片、技能、钩子、通道。
  • ACP：入站（Zed/OpenCode 等使用你的 Agent）与出站（OpenCode、Claude Code、CodeBuddy、Codex）。
  • 外部系统：浏览器、终端、远程桌面、远程 Android 控制、语音 STT/TTS。
↻

6. 自动化与触达

  • Cron：APScheduler；自然语言 / slash 创建；文本推送或跑 Agent；按 Agent 管理。
  • 外部事件：Webhook（HMAC）+ 连接器轮询；订阅、过滤、映射、合并窗口、限流、重试、死信、30 天保留。
  • 事件目标：专家 turn、团队 judge、MiniApp refresh/import。
  • 主动关怀：免打扰窗、随机频控、去重、预算、升级、责任范围、工具范围。
  • 通知：Dashboard WebSocket、IM 推送、审批卡片。
▦

7. 交付与 MiniApp

  • MiniApp：Agent 生成单文件 HTML + 控制面数据表；沙箱 iframe、SDK、能力清单。
  • 数据：多表、行级 CAS、幂等、导入/导出、PII 脱敏、备份/恢复。
  • 发布：只读公开链接、发布快照、表级可见性、限流、撤销。
  • AI：应用内只读数据助手（含图表）、一次性文本生成。
  • 工作台：个人多 Board、12 列网格、锁定、撤销、全屏、自动排列。
  • 交付物：团队目标可挂载文件、链接、文本或 MiniApp。
⛨

8. 安全与运维

  • 身份：JWT、角色、邀请码、OIDC、LDAP、验证码、登录锁定。
  • 执行控制：HITL 工具审批、app_delete 强制审批、Shell 命令防护、SSRF 校验。
  • 数据保护：PII 检测/脱敏、沙箱工作区、MiniApp 双层沙箱 + CSP + WebRTC 冻结。
  • 运维：安装向导、TLS / Let's Encrypt、systemd/launchd/Windows 服务、备份、更新、日志、资源限制。
  • 可观测：usage log、audit log、METRICS、API 文档、i18n（zh/en）。
能力边界提醒

“有功能”不等于“开箱即用”。连接器需要外部账号与授权；IM 通道需要平台应用凭证；知识库效果取决于文档质量与 embedding 模型；团队/数字员工仍是 Beta；MiniApp 的 R2/R3（外部服务、事件、统一调度、公开看板）尚未实现。销售承诺前请按第 07、08 节核对。

04 · 应用场景

8 个可落地的参考场景

每个场景都按“痛点 → 智总管组合 → 交付结果 → 衡量指标”展开，并注明当前边界。它们不是行业模板的替代品，而是销售做方案、产品做需求、研发做集成的共同语言。

销售产品
S1

个人 / 家庭超级助理

适合：个人、自由职业者、家庭共享部署 · 入口：Web / IM / Desktop

痛点

  • 信息散落在 IM、文档、网页和本地文件
  • 重复写周报、整理资料、设提醒
  • 通用聊天机器人不记得长期偏好

智总管组合

  • 专属 Agent + 长期记忆
  • 知识库 + 浏览器 + 文件工具
  • Cron 提醒 + IM 推送
  • 可选 MiniApp 个人台账

交付结果

  • 每日简报 / 周报
  • 个人资料库与问答
  • 日程、提醒、订阅
  • 家庭多用户共享

衡量指标

  • 每日节省时间
  • 周报生成耗时
  • 提醒到达率
  • 资料命中率
边界：需要一台可运行服务的机器与 LLM provider；长期记忆和大量文档会占用磁盘；不是“零配置”的消费级 App。
S2

中小企业 IM 团队助手

适合：10–200 人团队、部门 · 入口：飞书 / 钉钉 / 企微 / 微信 / Telegram / Discord

痛点

  • 知识和决策淹没在群聊里
  • 新人重复问同样的问题
  • 任务跟进靠人肉提醒

智总管组合

  • 多用户 + 多专家
  • IM 通道 + slash 命令 + 审批
  • 知识库 + 连接器
  • Cron 提醒 + 团队看板

交付结果

  • 群内可用的专家
  • 会议纪要 / 周报
  • 制度与产品问答
  • 任务提醒与升级

衡量指标

  • 群内响应时间
  • 知识命中率
  • 任务按时率
  • 人工转接率
边界：IM 通道需要平台应用与权限配置；团队/自治能力为 Beta；群聊策略、数据可见范围需在 POC 中确认。
S3

企业知识库与文档问答

适合：制度多、产品资料多、培训成本高的企业 · 入口：Web / IM

痛点

  • 文档找不到、版本乱
  • 回答不可追溯、不敢信
  • 权限边界不清

智总管组合

  • 知识库 + RAG + 引用
  • 本地 ONNX embedding（可选）
  • 连接器：腾讯文档 / Notion / Obsidian / 语雀 / Dify / WeKnora
  • ACL + 审计

交付结果

  • 可引用的企业问答
  • 培训 / 客服助手
  • 文档摘要与对比
  • 按用户/部门隔离

衡量指标

  • 回答命中率
  • 引用可追溯率
  • 搜索时间下降
  • 重复提问下降
边界：RAG 效果取决于文档解析、切分、embedding 与数据质量；不是“把所有文档丢进去就准确”；敏感文档需配合 ACL 与 PII 策略。
S4

销售 / 客户运营

适合：销售团队、客户成功、渠道运营 · 入口：IM / Web / MiniApp

痛点

  • 客户信息散落在表格、聊天、邮件
  • 跟进靠记忆，容易漏
  • 话术不统一，新人上手慢

智总管组合

  • 连接器：企查查、腾讯文档、邮箱、CRM/MCP
  • 记忆 + 知识库（产品/话术）
  • Cron 跟进提醒
  • MiniApp 客户跟进台账 / 漏斗
  • 只读公开链接

交付结果

  • 客户 360 台账
  • 每日跟进清单
  • 话术与方案草稿
  • 周报 / 漏斗看板

衡量指标

  • 跟进及时率
  • 人均客户数
  • 转化率
  • 新人上手时间
边界：外部 CRM/邮箱需连接器或 MCP 接入；客户敏感信息必须做 PII 标记与权限控制；公开链接只读，不能作为写入入口。
S5

运营数据台账与看板

适合：运营、门店、行政、财务、项目团队 · 入口：Web / MiniApp / 公开链接

痛点

  • Excel 多、版本乱、汇总慢
  • 数据只有少数人会做透视表
  • 分享靠截图，无法实时更新

智总管组合

  • 工作台「创建」：上传 Excel/CSV → 确认字段 → 生成看板/台账/进度板
  • 多表 + 行级 CAS + 导入/导出
  • 应用内数据助手（含图表）
  • 发布快照 + 只读公开链接
  • 多 Board 工作台

交付结果

  • 分钟级生成台账/看板
  • 手机可看的公开链接
  • 多人协作与数据维护
  • 门店/项目大屏

衡量指标

  • 报表制作时间
  • 数据更新频率
  • 查看人数
  • 手工汇总工时

06 · 技术架构

单进程、分层、可重建：研发视角的智总管

智总管的技术选择非常克制：一个 Python 进程、两个数据库选项、三个外部运行时库、没有外部队列。理解这一点，就能理解它的部署优势与扩展边界。

单一 Agent 运行时所有入口共用 Agent；差异在投影层处理行为一致、减少重复逻辑入口差异（富卡片/纯文本）要做适配

研发提示：单进程不是“简单”，而是“边界清晰”

依赖方向是 dashboard → api → infra → db/utils；infra/ 永不 import api/、cli/、launch.py。新增功能优先落在 infra/，HTTP 只做薄适配。多实例部署时，注意进程内锁/限流不是全局；数据库事务与 CAS 才是跨进程正确性的基础。

深入：MiniApp 的技术架构（简版）

数据：`light_apps` / `light_app_tables` / `light_app_rows` 等表；行级 CAS、幂等键、懒迁移。 界面：Agent 生成单文件 HTML，存在 Agent 工作区。 运行：固定 wrapper（`frame-src 'none'`）内嵌 App iframe（`sandbox=allow-scripts`），CSP 禁网，WebRTC/frame 冻结，宿主 bridge 按能力清单代调。 发布：只读公开 token；发布时冻结 HTML + 公开表结构，数据行实时读取；PII 实时脱敏。 边界：单表 2 万行 / 5 MB，不支持实时协同编辑、公开写入、复杂审批流。完整内容见 docs/miniapp-overview.md。

深入：外部事件与 Cron 的可靠性

Cron：APScheduler 进程级调度；任务行落库；支持文本推送或 Agent 回合；按 Agent 管理。 外部事件：Webhook HMAC + 连接器轮询 → external_events inbox → 订阅过滤 → external_deliveries outbox（条件 UPDATE 租约、指数退避、死信、30 天保留）→ 专家/团队/MiniApp target。 原则：先落库、再执行；崩溃后靠 DB 状态恢复，不依赖内存队列。 边界：语义级过滤、事件契约、严格顺序、公开事件 API 仍在后续设计（见 docs/miniapp-event-api-design.md）。

08 · 销售与方案指南

怎么讲、怎么问、怎么不踩坑

这一节是给销售和售前的“可执行话术”，但更像一份资格判断清单：先确认客户是否真的适合自托管多 Agent 平台，再谈功能。

销售

价值主张：按角色说

听众他们关心什么建议表达可证明的证据
老板 / 业务负责人降本、提效、可控“把重复工作交给可管理的数字同事；数据和流程留在自己手里。”专家/团队、Cron、MiniApp、预算与审批
IT / 安全负责人数据主权、权限、审计、运维“自托管、SSO/LDAP、ACL、PII 脱敏、审批、TLS、备份、可升级。”auth/ACL/audit/backup/setup 模块与配置
业务运营报表、台账、跟进、提醒“Excel 直接变成可维护的看板；手机打开只读链接就能看。”MiniApp 快速创建、数据表、公开链接、看板

最终用户好用、记得我、能动手“一个记得你偏好的助理，能在微信/飞书里直接帮你做事。”记忆、专家、IM、工具、MiniApp

常见异议与回答

客户问题建议回答不要这样说
“数据安全吗？”默认自托管，数据、密钥、会话在工作目录；支持 JWT/OIDC/LDAP、ACL、PII 脱敏、审批、审计、TLS。强隔离场景建议每部门/每环境独立实例。“绝对安全”“天然多租户隔离”
“只能用你们的模型吗？”可用 OpenAI 兼容、DashScope、Ollama 及多种预设；每个 Agent 可配 provider。“支持所有模型”
“部署复杂吗？”单进程；一键安装、PyPI、Docker、桌面端；octop init + octop run；可注册 systemd/launchd/Windows 服务。“零运维”
“能接我们的 IM 吗？”内置 10 个通道；也支持插件通道与自定义连接器/MCP。需要平台应用审核与凭证。“所有 IM 都开箱即用”
“能撑多少人？”单进程纵向扩展；小团队 SQLite，较大团队 PostgreSQL；跨节点用“每节点一个实例 + Bridge/外部协调”。“可以无限水平扩展”
“会不会很贵？”有 usage、配额、团队预算、本地模型、上下文/记忆优化；没有自动模型降级，需要按场景估算 token。“成本一定比人低”
“能做业务系统吗？”MiniApp 适合台账/看板/轻量数据维护；复杂审批、实时协同、公开写入不做。“可以替代 ERP/CRM”
“有审计吗？”有管理动作审计、usage、日志；工具调用级审计仍不完整，合规项目需单独评估。“全链路审计”
“能离线吗？”可用 Ollama 本地模型、本地 embedding；但连接器/IM/网页类能力仍依赖网络。“完全离线可用”
“能定制吗？”开源 MIT；连接器/MCP/插件/技能/专家/子代理/存储后端都可扩展。“什么都能定制”

资格判断（POC 前必问）

好信号

  • 有明确的重复工作或知识查询场景，能量化节省时间
  • 愿意提供 LLM API 或本地 GPU/Ollama
  • 有 IM/文档/CRM 等可接入系统，且有管理员配合
  • 接受“先单节点 POC，再扩团队”的节奏
  • 关注数据主权、权限、可运维性
  • 有 IT/运维能承担安装、备份、升级

危险信号

  • 要求多租户 SaaS、跨地域 HA、99.99% SLA
  • 要求完全无人值守、零审批的高风险操作
  • 没有模型预算，也不愿部署本地模型
  • 要求“所有系统一键接入”，但不提供账号/接口
  • 把 MiniApp 当 ERP/CRM 或复杂工作流引擎
  • 需要等保/密评等认证，但不愿走合规评估

建议的 3 个 Demo

1

5 分钟：IM 里的知识助手

在飞书/钉钉群 @ 专家，问一个知识库问题；展示引用、权限和“不知道就说不知道”。

证明：多用户 + IM + 知识库 + 权限。

2

10 分钟：Excel → 看板 → 链接

上传一份台账，确认字段，生成看板；发布只读链接，手机打开；用应用内助手问一个汇总问题。

证明：MiniApp + 数据 + 公开链接 + AI 助手。

3

15 分钟：团队目标 → 任务 → 交付物

设一个目标，主持人拆任务、派给成员；看板上看到任务状态；回填一个文件或 MiniApp 交付物。

证明：团队 + 任务 + 看板 + 交付物（Beta）。

不要承诺清单

  • 不要承诺“完全无人值守”“零人工审批”“100% 准确”。
  • 不要承诺多租户隔离、分布式集群、跨地域高可用。
  • 不要承诺替代 ERP/CRM/BPM 等权威业务系统。
  • 不要承诺所有连接器/IM 开箱即用；它们需要外部账号与授权。
  • 不要承诺 MiniApp R2/R3（外部服务、事件、统一调度、公开看板、迁移包、认证链接）。
  • 不要承诺自动模型降级、全链路工具审计、无限并发/行数。
  • 不要承诺等保/密评/行业认证；需要单独合规评估。
09 · 部署与交付

从安装到可交付：一份落地清单

智总管的部署形态很轻：一个进程、一个数据目录、一个 LLM provider。真正的交付工作量在账号、权限、连接器、知识库和场景配置上。

销售研发

安装方式

  • 一键脚本：macOS / Linux；Windows PowerShell/cmd；自动准备 Python 3.12 与 venv。
  • PyPI：pip install octop；可选 [local-embedding]。
  • Docker：docker compose -f docker/docker-compose.yml up -d；生产推荐。
  • 桌面端：Windows / macOS / Linux；FnOS NAS 包。
  • 源码：uv sync + make dev。

运行前提

  • Python 3.12+（安装脚本可代管）。
  • 一个可用的 LLM provider（API key 或本地 Ollama）。
  • 多核 CPU + 数 GB 内存 + 磁盘（模型缓存、知识库、工作区）。
  • 如需浏览器自动化：Playwright Chromium。
  • 如需远程桌面/Android：额外系统依赖与权限。

SQLite 还是 PostgreSQL？

场景建议理由
个人 / 家庭 / 小团队 POCSQLite（默认，WAL）零依赖、单文件、备份简单
较大团队 / 多用户 / 数据量增长PostgreSQL并发、运维、备份、扩展更稳
远程工作区 / 对象存储SQLite/PG + COS/S3/OSS/OBS控制面与工作区解耦
跨节点每节点一个智总管 + Bridge/外部协调智总管不做分布式集群

数据目录与备份

默认目录

~/.octop/
├── config.json        # 进程配置
├── env                # dotenv（可选）
├── octop.db           # SQLite 控制面
├── secrets/           # JWT / 通道密钥
├── agents/<id>/       # 每个 Agent 的工作区
├── plugins/           # 第三方插件
├── ssl/               # 自签证书（如使用）
└── logs/              # 运行日志

备份与运维

  • octop init：初始化 DB、JWT secret、管理员。
  • octop run：前台运行 API + Dashboard。
  • octop service start：注册 systemd / launchd / Windows 服务。
  • octop backup：手动/自动备份；配置保留数量。
  • octop update：在线更新。
  • TLS / Let's Encrypt：配置后自动签发。
  • 日志轮转 + systemd 资源限制（Linux）。

交付检查清单

  • 操作系统、CPU/内存/磁盘、网络与端口确认
  • 安装方式（脚本 / Docker / 桌面端）与数据目录确认
  • LLM provider、模型、API key/本地 Ollama 验证
  • 管理员账号、密码策略、验证码、登录锁定
  • SSO / LDAP / 邀请码 / 用户与角色
  • IM 通道应用创建、回调地址、权限与群策略
  • 连接器 OAuth/MCP 授权；确认只读/写范围
  • 知识库文档、embedding 模型、索引与权限
  • 专家/团队/数字员工配置与验收标准
  • MiniApp 数据导入、PII 标记、公开链接策略
  • TLS、备份、日志、监控、升级与回滚方案
  • 高风险工具审批、Shell 规则、SSRF/网络策略
  • POC 指标与验收口径（节省时间、命中率、任务完成率等）
销售提示：把“部署”与“场景配置”分开报价/排期

安装本身通常很快；真正耗时的是 IM 应用审核、连接器授权、知识库清洗、权限梳理和 POC 验收。方案里最好把“平台部署”和“场景落地”写成两个阶段，避免客户以为装完就能用。
