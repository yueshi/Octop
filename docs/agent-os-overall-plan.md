## 0. 摘要

**一句话**：老板设定带边界的目标，业务总控在边界内协调 Worker 干活，
越界时由内核的边界策略引擎拦下并推送审批；老板随时可以问「为什么」，
由解释 Worker 只读账本作答。

**三条核心判断**：

| # | 判断 | 依据 |
|---|---|---|
| 1 | **业务总控不做成内核之上的调度层**，而是应用层装配包里的「规划器 + 派发器 + 账本」 | Octop 的 `DecisionRunner` + `plan_dispatches` + `team_*` 已经是这个形态 |
| 2 | **总控无工具是治理需要，不能松**；但代价是它答不了「为什么」 | 无工具换来可审计、可 shadow、注入爆炸半径小 |
| 3 | **补一个解释 Worker**：只读账本、无调度权、无写工具 | 填补产品体验缺口，不触碰治理边界 |

**不做什么**：不新建调度层、不改造 Octop 内核为分布式、不让解释 Worker 拥有任何写权限。

### 0.1 已达成的共识

八条，按讨论时间排列：

| # | 共识 | 状态 |
|---|---|---|
| 1 | **Octop 是单节点平台，分布式要换形态**：不改 `SharedServices`、不引外部队列；用「每节点一个 Octop + 外部协调层」 | ✅ |
| 2 | **业务总控不是内核之上的调度层**：它是应用层装配包里的「规划器 + 派发器 + 账本」 | ✅ |
| 3 | **总控无工具是治理需要，不能松**；代价是它答不了「为什么」 | ✅ |
| 4 | **补一个解释 Worker**：只读、可对话、无写工具、无调度权、无审批权，且进第一批 | ✅ |
| 5 | **Super-agent 借鉴分两层**：方案 A（4 bug + 会话隔离 + accept_mode）现在做；方案 B（工单/直通/Mandate）是储备 | ✅ |
| 6 | **MiniApp 是投影层，不是权威源**；不承担审批、审计、多租户 | ✅ |
| 7 | **两种「协调」必须分开**：业务总控（节点内，现成）vs 节点协调（跨节点，待建） | ✅ |
| 8 | **没有任何一个角色同时拥有规划和执行权**（见 §3.4） | ✅ |

### 0.2 讨论中修正过的判断

记录这些是为了避免以后重复踩坑：

| # | 最初的判断 | 修正后 | 触发原因 |
|---|---|---|---|
| 1 | Octop「没有任何跨实例能力」 | **Bridge 已实现 3,778 行**：认证、隧道、寻址、历史拉取 | 核实 `infra/bridge/` |
| 2 | 4 个 bug + 大重构打包 30 人日 | 拆成方案 A（3–4 人日）/ 方案 B（储备） | 自我反思 |
| 3 | `autonomy_enabled` 与 `accept_mode` 重复 | **不重复**：前者是全关，后者是「只接明确请求」 | 语义核实 |
| 4 | `gate.py` 是纯函数 | **无副作用函数**（依赖时段/预算/限流计数） | 措辞准确性 |
| 5 | 工单 `done` 后停止 `pass` 订阅 | **保留并可恢复**（窗口 7 天 / 3 次 / 重校验） | 写业务故事时发现矛盾 |
| 6 | DeepSeek 的数字可作容量依据 | **不可比**（合成负载、编码任务、worker 用只耗时工具代替） | 自我审查 |

## 1. 问题与约束

### 1.1 业务场景

小企业连锁（首发美业），老板的核心诉求：

| 客户的怕 | 系统必须做到 |
|---|---|
| 怕 Agent 乱来 | 能力合约 + 边界策略 + 审计链 |
| 怕账单失控 | 成本硬顶 + 模型降级 |
| 怕用不起来 | 模板化上手 + 总控代替盯盘 |
| 怕数据出门 | 节点本地闭环，数据按合约分区 |

## 2. 分层：内核五原语 + 应用层装配包

### 2.1 五原语（内核）

| 原语 | 职责 | Octop 对应 |
|---|---|---|
| 目标入口 | 接收带边界的目标，分流到路径 A/B | `team_goals` + autonomy API |
| 能力合约注册表 | 声明「谁可以做什么、风险等级、是否可逆」 | **待建**（`SecurityPolicy` 是其底层的一半） |
| 边界策略引擎 | 放行 / 推送审批 / 拒绝（三态） | **待建** |
| 执行运行时 | 跑 Worker、管理会话与工作区 | `octop-harness` + `AgentManager` |
| 审计链 | 记录每一次能力调用与决策 | `audit_log`（管理动作）+ **待补能力调用** |

### 2.2 应用层装配包

应用层**不实现新机制**，只是把内核能力装配成业务形态：

| 装配物 | 形态 | Octop 落点 |
|---|---|---|
| 目标模板 | 「本月会员活跃度 +5%」这类预设目标 | 专家模板的 `manifest.json` |
| 能力合约实例 | 「发优惠券：不可逆、金额阈值 50 元、需审批」 | 合约注册表的配置行 |
| 策略预设 | 「每日最多 200 条触达、预算 50 元」 | `autonomy_policy` |
| Worker 组合 | 巡检 / 日报 / 触达 / 前台 / 解释 | 专家模板 + 团队 |

**关键**：`infra/agents/experts/library/` 已经是这个形态——
`manifest.json`（装配声明）+ `SOUL.md`（角色）+ `skills/`（能力）。
业务总控可以直接做成一个专家模板，不需要新机制。

### 2.3 为什么不在内核之上加调度层

| 问题 | 说明 |
|---|---|
| 职责重叠 | 总控若要判断「派给谁、花多少预算、要不要审批」，必须知道能力合约与目标边界——这些在内核里。放在外面要么重复实现，要么频繁回调 |
| 语义冲突 | 路径 A/B 的分流应由「目标接入层」完成，总控再插一手会让数据流变乱 |
| 场景不需要 | 小企业老板要的是「有人替我盯住」，不是「总控中心界面」。盯住用一个总控 Worker 就够 |

## 3. 业务总控

### 3.1 它是什么：规划器 + 派发器 + 账本

**不是**一个 Agent，而是三个互相制约的部件：

| 部件 | 职责 | Octop 实现 | 有无工具 |
|---|---|---|---|
| **Planner** | 看快照，输出计划 JSON | `DecisionRunner`（`infra/agents/teams/decision.py:462`） | **无** |
| **Dispatcher** | 校验并派发，算依赖/并发/预算 | `plan_dispatches`（`infra/agents/teams/dispatcher.py:102`） | 确定性代码 |
| **Ledger** | 记录决策、事件、任务状态 | `team_decisions` / `team_events` / `team_tasks` | — |

Planner 的实现（`infra/agents/teams/decision.py:771`）：

```python
def provider_plan_fn(...):
    """Default plan_fn: one plain provider chat call on the team's model.

    Deliberately bypasses the harness graph — the decision turn must carry
    no tools (§6.3) and must not touch the room thread (§6.4).
    """
    async def plan_fn(prompt, team_id):
        chat_model = build_probe_chat_model(provider_row, model_id=model_id)
        response = await chat_model.ainvoke([HumanMessage(content=prompt)])
        return _message_text(response), usage
```

**它直接构造 chat_model，完全绕过 harness graph。** 没有 tool registry、没有图、没有多轮。

### 3.2 计划要过四道闸

```
LLM 输出 JSON
  │
  ├─ 1. DecisionPlan.model_validate_json        结构校验（decision.py:333）
  ├─ 2. validate_decision_plan(...)             成员身份 / 任务引用 / 版本（decision.py:646）
  ├─ 3. plan_dispatches(...)                    依赖 / 并发 / 忙碌 / 预算（dispatcher.py:102）
  └─ 4. Worker 执行时的能力合约                  风险等级 / 边界三态
```

**四道闸是「总控没有调度权」的具体含义。** 模型只能表达意图，不能产生效果。

### 3.3 无工具设计的收益与代价

| 收益 | 说明 |
|---|---|
| 消除「边做边改计划」 | 计划一次成文，是契约；事后可精确复现 |
| 成本可预测 | 一次调用 vs 多轮工具循环，差一个数量级 |
| 注入爆炸半径小 | 坏计划要过四道闸；有 bash 工具则第一道闸不存在 |
| 可 shadow 运行 | `apply_plan=False` 只落库不执行（`decision.py:465`） |
| 派发确定 | 排序/依赖/并发不让模型算 |

| 代价 | 说明 |
|---|---|
| 不能「先查再规划」 | 所需信息必须预先在 snapshot 里（`decision.py:243-290`） |
| 错误不能当场自纠 | 只能等下一次 decision（有 cooldown） |
| snapshot 成为质量瓶颈 | 少了瞎猜，多了 token 膨胀 |
| **总控是函数，不是对话者** | **老板问「为什么」时答不了——这是解释 Worker 的由来** |

### 3.4 决定各层级能做什么的能力边界

| 角色 | 能不能规划 | 能不能派发 | 能不能执行 | 能不能审批 |
|---|---|---|---|---|
| Planner（LLM） | ✅ | ❌ | ❌ | ❌ |
| Dispatcher（代码） | ❌ | ✅ | ❌ | ❌ |
| Worker（Agent） | ❌ | ❌ | ✅（受合约约束） | ❌ |
| 边界策略引擎（内核） | ❌ | ❌ | ❌ | ✅ |
| 老板 | ✅（改目标） | ❌ | ❌ | ✅ |

**没有任何一个角色同时拥有规划和执行权**——这是整套治理的地基。

### 3.5 待补：协调合约

现状的边界是「是不是团队成员」（`member_ids_fn`），**不是「有没有协调权限」**。

需要一份显式的协调合约，声明：

```
总控 Worker 可以协调：
  - 巡检 Worker   （只读，无金额）
  - 日报 Worker   （只读，无金额）
  - 触达 Worker   （写，金额上限 50 元，需审批）
  - 前台 Worker   （写，预约变更，改价需审批）

不得协调：
  - 定价 Worker   （需老板直接授权）
```

**落点建议**：专家模板 `manifest.json` 加一节 `coordination`，
由 `validate_decision_plan` 校验 assignee 是否在允许列表内（小改动）。

## 4. 解释 Worker（新增）

### 4.1 为什么需要

总控无工具、单次成文。老板会问：

- 「今天为什么没给王女士发优惠券？」
- 「昨天各店都做了什么？」
- 「这个任务卡在哪了？」
- 「上次那条触达是谁批的？」

**总控答不了。** 它只输出过一份 JSON，没有对话能力，也没有查历史的能力。

现状下答案在 `team_decisions` 的 `reason` 字段和 `team_events` 里，
但要人去翻数据库——这等于没有。

### 4.2 它是什么

> **一个只读的、能对话的账本解释器。**

| 维度 | 定义 |
|---|---|
| 身份 | 普通 Agent（有工具、有多轮），但工具全都是只读的 |
| 数据范围 | 同一个 agent / team 的账本，不能跨用户 |
| 权限 | **读**：决策、事件、任务、审计、边界拒绝记录<br>**写**：无（没有任何写工具） |
| 触发 | 老板主动提问，或定时生成日报摘要 |
| 模型 | 廉价模型即可（读账本 + 组织语言，不需要复杂推理） |
| 会话 | 独立会话 `agent:{id}:explain`（与工作会话隔离） |

### 4.3 它不是什么

| 不是 | 原因 |
|---|---|
| 不是总控 | 没有规划权、没有派发权 |
| 不是审批者 | 不能批准任何动作 |
| 不是执行者 | 没有写工具，连发消息都要走 gateway 的显式回复通道 |
| 不是审计链 | 它读审计，不写审计（它自己的调用会被审计） |

### 4.4 数据来源与工具设计

| 工具 | 读什么 | 现有 repo |
|---|---|---|
| `explain_decisions` | 决策列表与详情（含 `reason`、plan JSON、校验结果） | `TeamDecisionRepo.list_by_team`（`infra/db/repos/team_decisions.py:176`） |
| `explain_events` | 事件账本（谁触发了什么） | `TeamEventRepo.list_after`（`infra/db/repos/team_events.py:111`） |
| `explain_tasks` | 任务状态、assignee、阻塞原因 | `TeamTaskRepo` |
| `explain_audit` | 管理动作与（未来的）能力调用审计 | `AuditRepo.query`（`infra/db/repos/audit.py:81`） |
| `explain_boundary` | 被边界策略拒绝/推送的动作 | **待建**（依赖边界策略引擎的拒绝记录） |

工具全部带 `since` / `until` / `limit` 参数，返回摘要 + 分页游标（Inline & Spill）。

### 4.5 回答模式映射

| 老板的问题 | 查询路径 |
|---|---|
| 「为什么没做 X」 | `explain_decisions(since=…)` → 找相关 plan → 读 `reason` 与校验结果 |
| 「昨天做了什么」 | `explain_tasks` + `explain_events` 按时间聚合 |
| 「这个任务卡在哪」 | `explain_tasks(task_id)` → 状态 + `active_wait_id` + 依赖链 |
| 「谁批的」 | `explain_audit(action=…)` + `hitl_pending` 记录 |
| 「为什么被拒」 | `explain_boundary` → 拒绝原因与触发的合约条款 |

**关键**：解释 Worker **不做推断**。它只做「检索 + 组织语言」。
如果账本里没有记录，它必须回答「没有记录」，不能编。

这一条要写进它的 SOUL.md，并在测试里断言。

### 4.6 权限与隔离

| 边界 | 规则 |
|---|---|
| 跨用户 | 禁止。查询强制带 `agent_id` / `team_id`，由 router 按 owner 校验 |
| 跨团队 | 禁止。只能读自己所属团队的账本 |
| 写操作 | 无工具。唯一的输出是通过 gateway 回复给提问者 |
| prompt injection | 账本里可能含外部事件内容（不可信），但解释 Worker 无写工具，爆炸半径仅为「说错话」 |

### 4.7 成本控制

| 手段 | 说明 |
|---|---|
| 廉价模型 | 读账本 + 组织语言，不需要强推理 |
| 缓存 | 常见问题（「今天怎么样」）按小时缓存答案 |
| 限流 | 每用户每分钟 N 次（复用 `SlidingWindowLimiter`） |
| 摘要优先 | 默认返回聚合摘要，明细按需展开 |

### 4.8 与 MiniApp 看板的关系

| | MiniApp 看板 | 解释 Worker |
|---|---|---|
| 形态 | 结构化数字与图表 | 自然语言追问 |
| 触发 | 打开页面 | 主动提问 |
| 回答 | 「今天做了 12 件事」 | 「为什么第 3 件没做成」 |
| 数据 | MiniApp 表 | 账本 |

**两者互补，不重叠。** 看板负责「是什么」，解释 Worker 负责「为什么」。

### 4.9 与总控的关系

```
老板 → 目标（带边界）
        │
        ▼
     Planner（无工具）──→ 计划 JSON ──→ Dispatcher ──→ Worker 执行
        │                                              │
        └────────────── 写入账本 ←─────────────────────┘
                            │
                            ▼
                     解释 Worker（只读）
                            │
                    自然语言回答「为什么」
```

**解释 Worker 是账本的下游消费者，不参与任何决策。**

## 5. 执行层：Worker 类型

| Worker | 路径 | 能力 | 审批边界 |
|---|---|---|---|
| **业务总控** | B | 协调其他 Worker（受协调合约限制） | 自身无审批权 |
| **巡检** | A | 只读检查 | 无 |
| **日报** | A | 只读汇总 + 写 MiniApp | 无 |
| **触达** | A | 企微群发、标签 | 超预算/超人数需审批 |
| **AI 前台** | A | 接听、预约确认 | 改价/取消已付定金需审批 |
| **解释** | — | 只读账本 | 无 |

**共同约束**：所有 Worker 都只能通过能力合约行动，动作全部进审计链。

## 6. 治理平面

### 6.1 能力合约

每个能力（工具）声明：

| 字段 | 示例 |
|---|---|
| `tool` | `wecom.send_campaign` |
| `reversible` | `false` |
| `money_threshold` | `50`（元） |
| `external_commitment` | `true`（对外承诺） |
| `risk_level` | `high` |

**这是待建的第一优先级**：没有它，边界策略引擎无从实现。

### 6.2 边界三态

| 结果 | 条件 | 动作 |
|---|---|---|
| 放行 | 合约允许且未越界 | 直接执行 |
| 推送审批 | 不可逆 / 超金额 / 对外承诺 / 越边界 | 生成审批预览，推给老板 |
| 拒绝 | 合约禁止 | 拒绝并记审计 |

**层级关系**：边界三态在 `SecurityPolicy`（工具级 HITL）**之上**。
不是替换它，是先粗判（90% 放行），越界才下沉到 SecurityPolicy 精判。

### 6.3 审计链

现状 `audit_log` 只记录管理动作（agent 增删、SSO 配置、备份）。
需要补：**每一次能力调用**（谁、什么合约、边界判断结果、执行结果）。

**落点**：harness 的工具执行钩子 + 新的 `capability_audit` 表（或扩 `audit_log`）。

### 6.4 成本

| 层 | 现状 | 待补 |
|---|---|---|
| 硬顶 | `budget_remaining` 按日 token（已生效） | 金额维度 |
| 降级 | 无 | local → cheap → premium |
| 归集 | 按 agent/team | 按目标 / 按 Worker |

## 7. 双模执行

| | 路径 A：确定性工作流 | 路径 B：目标导向编排 |
|---|---|---|
| 适用 | 送水工单、预约确认、库存查询 | 本月会员活跃度 +5%、降低空置率 |
| 驱动 | 工作流引擎 | Planner + Dispatcher |
| 审批 | 按能力合约风险等级 | 审批方向与预算，不是每一步 |
| Octop 现状 | cron + `team_tasks`，**无工作流引擎** | ✅ 完整 |
| 缺口 | 外挂状态机或把流程建模成 task 依赖 | — |

**汇合点**：所有能力调用经过同一个能力合约、同一个边界策略引擎、同一个审计链。

## 8. 分布式形态

### 8.1 两种「协调」，不要混淆

| | 业务总控 | 节点协调 |
|---|---|---|
| 协调什么 | 巡检 / 日报 / 触达等 Worker | 盒子 A / 盒子 B / 中心 |
| 位置 | **节点内，执行层** | **跨节点，基础设施层** |
| Octop 现状 | ✅ 现成（团队编排） | ❌ 没有 |
| 实现 | 专家模板 + 团队编排 | 自研或复用 Bridge |

**本文 §3–§4 说的都是前者。** 后者见 §8.2。

### 8.2 分布式：不改内核，换形态

```
┌─────────────────────────────────────────────┐
│ 中心域（集装箱）                              │
│   Octop 实例（PostgreSQL）                    │
│   + 节点协调 Agent                            │
│      · 策略下发：把 bounds 推到各盒子          │
│      · 跨节点关联诊断                          │
│      · 审计汇总                                │
└──────────────┬──────────────────────────────┘
               │ 只同步「策略 / 审计 / 待办」
     ┌─────────┴─────────┐
     ▼                   ▼
┌──────────┐        ┌──────────┐
│ 盒子 A   │        │ 盒子 B   │
│ Octop    │        │ Octop    │
│ SQLite   │        │ SQLite   │
│ 本地闭环  │        │ 本地闭环  │
└──────────┘        └──────────┘
```

**复用 Bridge**（`infra/bridge/`，3,778 行）已有的跨实例认证、隧道、寻址。
缺的是节点发现、策略下发、批量审计汇总。

**不要**把 `SharedServices` 改成分布式——那是与 ADR 001 的核心假设对抗。

## 10. 美业 MVP

### 10.1 范围

| Worker | 路径 | 上线批次 |
|---|---|---|
| AI 电话前台 | A | **第一批** |
| 旧客触达 | A（定时触发变体） | **第一批** |

| 解释 Worker | — | **第一批**（没有它老板无法追问） |
| 业务总控 | B | 第二批 |
| 巡检 | A | 第二批 |

### 10.2 为什么解释 Worker 进第一批

没有它，老板面对的是一个「默默干活但不解释」的系统。
一旦出现「为什么没发」的疑问而无处可问，信任就断了。

**它的成本很低**（廉价模型 + 只读），但决定了产品能不能被信任。

### 10.3 第一批的前置门槛

| 门槛 | 验证方式 |
|---|---|
| 盒子硬件能跑 | 实机压测：Python 3.12 + FastAPI + LangGraph + 多 agent 并行 |
| 电话延迟可接受 | TCCC → agent → LLM 首 token 的端到端时延 |
| 能力合约 schema 定稿 | 评审通过 |

## 12. 风险与开放问题

| 风险 | 影响 | 缓解 |
|---|---|---|
| snapshot 设计不当 | 总控瞎猜或 token 膨胀 | 把 snapshot 字段当产品契约维护，定期评审 |
| 解释 Worker 被诱导编造 | 老板被误导 | SOUL.md 写死「无记录就说无记录」+ 测试断言 |
| 能力合约漏标风险等级 | 越界动作被放行 | 默认拒绝：未标注 = 高风险 |
| 协调合约过宽 | 总控越权调度 | 白名单 + `validate_decision_plan` 校验 |
| 两套状态机并存 | 认知负担 | 团队任务 vs 工单（方案 B）不互引状态 |
| 盒子硬件不足 | MVP 跑不起来 | 阶段 1 前实机压测 |
| 解释 Worker 成本 | 老板频繁追问 | 缓存 + 限流 + 廉价模型 |

### 开放问题

| # | 问题 | 待定 |
|---|---|---|
| Q1 | 解释 Worker 是否也回答「建议怎么做」？ | 建议：不。它只解释已发生的事，建议归总控 |
| Q2 | 解释 Worker 的会话是否与老板 DM 合并？ | 建议：独立，避免污染工作转录 |
| Q3 | 节点协调 Agent 是普通 Agent 还是独立服务？ | 建议：普通 Agent（复用团队编排），但它跨节点读账本需要额外权限 |
| Q4 | 路径 A 用外挂工作流引擎还是建模成 task 依赖？ | 看第一批的实际流程复杂度 |

### 13.1 单节点内（一个盒子 / 一个 Octop 实例）

```

                               │

│  → 跟踪 → 回执 → 升级         │  │  │ Planner（LLM，无工具）    │  │

│                              │  │  ┌──────────▼───────────────┐  │
```

### 13.2 跨节点（阶段 3）

```
                    ┌────────────────────────────────┐
                    │ 中心域（集装箱）                 │
                    │  Octop 实例（PostgreSQL）        │
                    │  + 节点协调 Agent               │
                    │    · 策略下发（bounds → 盒子）   │
                    │    · 审计汇总                    │
                    │    · 跨节点关联诊断               │
                    │    · 任务重派                    │
                    └───────────────┬────────────────┘
                                    │ Bridge（复用现有实现）
                    只同步「策略 / 审计 / 待办」，不同步 session
              ┌─────────────────────┴─────────────────────┐
              ▼                                           ▼
    ┌──────────────────┐                        ┌──────────────────┐
    │ 盒子 A            │                        │ 盒子 B            │
    │  完整 Octop       │                        │  完整 Octop       │
    │  SQLite 本地闭环   │                        │  SQLite 本地闭环   │
    │  断网可执行本地目标 │                        │  断网可执行本地目标 │
    └──────────────────┘                        └──────────────────┘
```

**跨节点不做的事**：不做分布式事务、不做会话级状态迁移、不做共享上下文。
状态迁移退化为「任务在中心重新分派」。

### 13.3 一次完整的数据流

以「周女士的订单风险评估」为例：

```
1. 外部事件（订单 webhook）
      │  落 external_events + external_deliveries
      ▼
2. 目标接入层判断：
      确定性触发 → 路径 A
      需要判断   → 路径 B
      │
      ▼
3. 【路径 B】Planner 看 snapshot：
      {runtime, goal, tasks, waits, events, recent_decisions, metrics, policy}
      → 输出 plan JSON：
        {"task_ops": [{"op":"create", "title":"评估订单 X", "assignee":"巡检"}]}
      │
      ▼
4. 四道闸：
      结构校验 → 成员/引用校验 → 依赖/并发/预算 → 能力合约
      │
      ▼
5. Dispatcher 派工 → Worker（隔离会话）
      │
      ▼
6. Worker 执行时每一次工具调用：
      能力合约 → 边界三态
        ├─ 放行 → 执行
        ├─ 推送 → hitl_pending → 老板确认
        └─ 拒绝 → 记录
      │
      ▼
7. 全链路写入账本：
      team_decisions（含 reason）· team_events · 审计链
      │
      ├──▶ 老板看板（MiniApp 投影）
      └──▶ 解释 Worker（只读）→ 回答「为什么这么处理」
```

### 13.4 四条不变量

这四条是判断任何改动是否偏离目标的标准：

| # | 不变量 | 违反的后果 |
|---|---|---|
| 1 | **规划与执行分离** | 有工具的总控会边做边改，审计失效 |
| 2 | **审批权只在内核** | 业务层有审批权 = 可以绕过边界 |
| 3 | **展示层不是权威源** | MiniApp 承担权威 = 数据不一致 |
| 4 | **节点自包含** | 跨节点共享状态 = 断网即停 |

**一句话**：Octop 负责「安全地执行」，总控负责「决定做什么」，
解释 Worker 负责「说明为什么」。三者通过账本连接，通过能力合约约束，通过审计链留痕。
分布式不在这套东西里面——它是外面的一层，用「每节点一个 Octop」实现。
