# Super-agent 控制面：一个具体业务案例

Status: design record / draft
Date: 2026-11-07
Scope: `docs/superagent-borrowing-design.md` 的端到端叙事版。用一家小电商的一夜加一天，
把 Gate 的三档拒绝、accept mode 的观察期、工单、会话隔离、直通、提问与恢复全部走一遍。

断言规格见 `docs/superagent-borrowing-e2e.md`。本文只讲故事，技术锚点用括号标出。

---

## 0. 场景设定

**杭州山雾茶事**，一家卖岩茶和红茶的小电商，三个运营。

| 角色 | 说明 |
|---|---|
| **李薇** | 运营负责人，Octop 的普通用户，账号 `liwei` |
| **小巡** | 李薇从专家库建的 agent，职责是盯订单异常。会话里她叫它「小巡」 |
| **订单系统** | 自建，有 webhook。订单创建 / 付款 / 退款各推一条 |
| **订单看板** | 一个 light app，每 15 分钟从订单系统同步一次，给运营看数据 |

小巡的初始配置（11-06 晚，李薇花十分钟配好）：

```
职责范围：销售订单
主动规则：单笔金额超过 5000 元时跟进
接受模式：观察（observe）        ← 关键
活跃时段：09:00 – 22:00
每日任务上限：20
```

李薇没敢直接开「自动」。她想先看看这东西到底会干什么。

---

## 1. 第一夜：观察模式下的两次"什么都没发生"

### 23:40 —— 一笔差点漏掉的订单

老客户「陈先生」下了一单岩茶，8200 元。

```
POST /api/hooks/src_orders
X-Octop-Event-Type: order.created
X-Octop-Event-Id: ord-20261106-8841

{"order_id":"ord-20261106-8841","customer":"陈先生","amount":8200,"items":["正岩肉桂 250g ×2"]}
```

**系统里发生的事**（李薇什么都看不到）：

1. 事件入库，摘要「陈先生 下单 ¥8,200，正岩肉桂 250g ×2」
2. Gate 第 2 步：事件类型 `order.created` 命中订阅过滤 → 放行
3. Gate 第 3 步：职责范围「销售订单」命中 → 放行
4. Gate 第 4 步：现在 23:40，不在 09:00–22:00 → **deferred**
5. 事件被标记为「延后」，挂着，不丢

> 这是设计里最容易做错的一步。如果按"不活跃时段就丢弃"，这笔订单第二天永远没人看。
> `deferred` 的语义是**稍后再做**，不是**不做**。

### 02:14 —— 又来了一个大单，但不该今天做

另一位客户下了 9200 元的单。同样 deferred，排到次日 09:00。

### 09:00 —— 两个事件同时被取回

小巡的活跃时段开始，系统把挂着的两条事件取回，一起送进研判。

**这一轮只调用了一次模型**（批量研判，对应设计 §5.4）：

| 订单 | 金额 | 客户 | 研判结果 |
|---|---|---|---|
| ord-20261106-8841 | ¥8,200 | 陈先生 | 命中「金额 > 5000」→ 本来会跟进 |
| ord-20261107-1002 | ¥9,200 | 周女士 | 命中「金额 > 5000」→ 本来会跟进 |

但接受模式是 **observe**。所以两条都只落记录，**不开工**。

李薇早上打开面板，看到「工作记录」里多了两条：

```
┌─ 工作记录 ────────────────────────────────────────┐
│ 11-07 09:00  本来会做 · 单笔金额超 5000              │
│   陈先生 下单 ¥8,200（正岩肉桂 250g ×2）            │
│   命中规则：over_5000                               │
│   [查看事件原文] [转为自动]                          │
│                                                     │
│ 11-07 09:00  本来会做 · 单笔金额超 5000              │
│   周女士 下单 ¥9,200                                │
│   命中规则：over_5000                               │
│   [查看事件原文] [转为自动]                          │
└─────────────────────────────────────────────────────┘
```

**小巡的 DM 会话里一条消息都没有。** 这是设计里会话隔离的直接效果——观察期的记录
不该污染李薇跟小巡的正常对话。

> 如果没做会话隔离，这两条会出现在李薇的聊天窗口里，她会以为自己被半夜打扰了。

### 09:30 —— 李薇点了「转为自动」

她看完两条记录，觉得规则没问题。在面板上把接受模式从「观察」改成「自动」。

（`PUT /api/agents/{agent_id}/autonomy-policy`，`accept_mode: "auto"`）

策略版本随之变化。系统记下这次变更，但**不动任何已结束的记录**——
那两条 declined 的工单保持原样，作为决策审计留档。

## 2. 10:05 —— 真正的第一次开工

周女士的第二笔订单到了。

```
POST /api/hooks/src_orders
X-Octop-Event-Type: order.created
X-Octop-Event-Id: ord-20261107-1033

{"order_id":"ord-20261107-1033","customer":"周女士","amount":12600,"items":["老丛水仙 500g ×3"]}
```

### 这一刻系统做了什么

```
Gate（程序级，0 次模型调用）
  ✓ 源启用          ✓ 类型命中
  ✓ 职责范围命中     ✓ 10:05 在时段内
  ✓ 今日额度 3/20    ✓ 未触发限流
        │
        ▼
Assessor（语义级，1 次模型调用）
  规则 over_5000 → 命中
  证据：金额 12600 > 5000
  决定：accept
        │
        ▼
建工单
  ticket_id: wt_01J...
  strength: inferred（推断出来的，不是人直接要求的）
  policy_version: a3f9c2...
  scope: 职责=销售订单, 预算=当日剩余 17
        │
        ▼
派工 → 隔离会话 agent:xiaoxun:work:wt_01J...
```

### 小巡这一轮看到了什么

不是一段摘要字符串，而是**事件卡 + 按需读取入口**（设计 §5.10 Inline & Spill）：

```
【工作】订单金额异常跟进

事件触发
  来源：订单系统
  类型：order.created
  时间：2026-11-07 10:05
  摘要：周女士 下单 ¥12,600，老丛水仙 500g ×3
  事件 ID：ord-20261107-1033
  （完整 payload 未展开，需要时用 work_read_event 读取）

同一订单的近期事件
  10:05  周女士 下单 ¥12,600        ← 当前
  昨日 09:00  周女士 下单 ¥9,200     ← 同一位客户

进行中的相关工单
  无

权限范围
  职责：销售订单
  本次授权：推断（依据规则 over_5000，策略版本 a3f9c2）
```

小巡看到「周女士昨天刚下过 9200，今天又下 12600」，决定先查一下。

它调用 `work_read_event("ord-20261107-1033")` 拿到完整 payload，
发现收货地址跟昨天那单不同（一个西湖区，一个余杭区）。

它又查了订单列表工具，发现**周女士三天内已经下过 4 单，累计 3.8 万元，收货地址有 3 个不同小区**。

### 10:12 —— 小巡提问了

它没有直接下判断，而是把问题抛给李薇（这在设计里叫 `attention`，工单转 `blocked`）：

```
┌─ 需要你决定 ─────────────────────────────────────┐
│ 周女士三天内 4 单、累计 ¥38,400，收货地址 3 个不同小区。│
│ 这批订单要不要先联系客户本人确认，再安排发货？        │
│                                                   │
│ [确认后发货] [先联系客户] [标记为正常，不处理]        │
└───────────────────────────────────────────────────┘
```

**这条通知立刻推送**，不等 15 分钟的批量窗口——因为它属于"人必须行动"。

工单状态：`working` → `blocked`，展示阶段「需人工：等待回答」。

### 10:14 —— 李薇选了「先联系客户」

她的回答作为一条输入回到工单，工单从 `blocked` 恢复 `working`，小巡继续。

（注意：这个"继续"发生在**同一个隔离会话**里，小巡记得它刚才查过什么，
不需要李薇重新解释一遍背景。）

### 10:17 —— 完成

小巡做完后续动作（在订单系统打了「待核实」标签，起草了一条给客户的确认消息），
工单转 `done`，结果回到收件箱：

```
┌─ 已完成 ─────────────────────────────────────────┐
│ 周女士订单 ord-20261107-1033 已标记「待核实」      │
│                                                   │
│ 做了什么：                                         │
│ · 查了该客户 3 天内 4 笔订单，累计 ¥38,400         │
│ · 在订单系统加了「待核实」标签                      │
│ · 起草了给周女士的确认消息（未发送，等你过目）       │
│                                                   │
│ [查看完整过程] [发送确认消息]                       │
└───────────────────────────────────────────────────┘
```

**李薇的 DM 会话里依然只有她跟小巡的日常对话。** 这一整轮的工作记录在
「工作记录」分组里，点进去能看到每一步。

## 3. 14:20 —— 直通：同一条订单线的后续事件

周女士付款了。

```
POST /api/hooks/src_orders
X-Octop-Event-Type: order.paid
X-Octop-Event-Id: ord-20261107-1033-paid

{"order_id":"ord-20261107-1033","amount":12600,"paid_at":"14:20:07"}
```

**这一次研判没有被调用。**

为什么？因为工单 `wt_01J...` 建立时订阅了这条订单的事件流（`stream_key = order:ord-20261107-1033`，
模式 `pass`）。后续事件直接进工单，不再走 Gate 和 Assessor。

| 项 | 结果 |
|---|---|
| Assessor 调用次数 | **不变**（仍是 0 次增量） |
| 新工单 | **没有新建**（这条订单已经有工单了） |
| 原工单 | 从 `done` 回到 `working`，成为这次付款事件的归属 |
| 授权 | 不变——直通输入**不授予新权力**，工单还是原来的 scope |

小巡被唤醒，看到「周女士付款了」，于是把订单系统里的「待核实」标签撤掉，
工单重新 `done`。

> 这种"结束又被拉回"有边界：默认只能在工单结束后 7 天内恢复，最多恢复 3 次，
> 且每次恢复前要重校验授权（规则还开着吗？接受模式还是自动吗？）。
> 超出窗口就不再自动恢复，那个事件会当成新事情重新走一遍流程。
> 李薇主动停掉的工单永远不恢复。

> 这就是设计里直通（pass-through）的价值。没有它，同一条订单线的每个事件
> 都要重新过一遍 Gate 和研判，既慢又费钱。DeepSeek 实测里，去掉直通后协调者
> 决策数涨了 30%、读缓存 token 涨了 37%，完成时间却几乎没变——说明这些重复决策
> 纯属浪费。

## 4. 同一天里，"什么都不该做"的三种情况

不是每条事件都值得开工。这一天里还有三条事件，分别对应三种不同的"不做"：

### 4a. 10:40 —— 系统在喊，但不是我们的事

订单系统推送了一条**供应商采购单**：

```
X-Octop-Event-Type: purchase.created
{"po_id":"PO-338","supplier":"福鼎白茶厂","amount":28000}
```

| | |
|---|---|
| Gate 第 3 步 | 职责范围是「销售订单」，这是采购 → **filtered** |
| 结果 | 事件入库，标记「已过滤 · 超出职责范围」 |
| 工单 | 无 |
| 小巡 | 没被调用 |

李薇在「工作记录」的「已过滤」标签里能看到它，还能看到过滤原因。
**如果她发现这是漏判，可以手动点「重新评估」。**

### 4b. 11:02 —— 该做，但等一下

一笔 6800 元的订单。金额超过 5000，本该跟进。

但**今日任务数已经 19/20**，这条会顶到上限。

| | |
|---|---|
| Gate 第 5 步 | 今日额度用尽 → **deferred** |
| 结果 | 挂起，次日 09:00 取回 |
| 工单 | 暂不建 |

不是不做，是**明天做**。第二天 09:00 它会被自动取回，正常走完流程。

### 4c. 11:15 —— 做，但太频繁了

同一分钟里有 5 条订单事件涌进来（一个大促活动）。订阅配置了每分钟最多 3 条。

| | |
|---|---|
| Gate 第 6 步 | 第 4、5 条 → **skipped** |
| 结果 | 落一条「已跳过 · 限流」记录，事件本身仍在事件列表里 |
| 工单 | 无 |

> 现状代码在这里是直接 `continue` 掉——事件凭空消失，既不留记录也不报错。
> 李薇永远不知道有两条订单没人看。设计把它改成落一条 skipped 记录，
> 至少可查、可手动重放。

**三种"不做"的区别**：

| 标记 | 含义 | 会自己恢复吗 |
|---|---|---|
| `filtered` | 不该做 | 不会 |
| `deferred` | 稍后再做 | **会**，到时间/有额度自动取回 |
| `skipped` | 这次不做 | 不会，但可手动重放 |

## 5. 11:30 —— 数据看板那边也来了一条

订单看板每 15 分钟同步一次订单系统。11:30 这次同步完，发现「今日销售额」比过去
7 天同期均值高出 240%。

这条**同步结果本身**被当成事件推了出去（设计 §5.14 数据平面）：

```
X-Octop-Event-Type: app.sync.threshold
{"app":"订单看板","table":"daily_sales","metric":"今日销售额","value":48200,"baseline":19800}
```

小巡也订阅了这个源。于是：

1. 事件走**和 UC-1 完全相同的流水线**：Gate → Assessor → 工单 → Worker
2. 研判命中「销售异常波动」规则 → 建工单
3. 小巡被唤醒，做的是"查一下今天到底卖了什么"

**这就是数据和主动工作合流的意义**：李薇不需要为"数据变化"单独配一套告警规则，
看板的数据变化自动变成小巡的工作。同一套 Gate，同一套工单，同一套审计。

## 6. 15:40 —— 中断，以及为什么没有重复干活

15:40，服务器因为一次运维操作重启了。当时小巡正在处理一个订单备注。

重启后系统扫查发现：

| 工单 | 中断时的状态 | 重启后的处置 |
|---|---|---|
| wt_A（备注处理） | 已开始执行（`started_at` 非空） | **不自动重跑**，转 `needs_review`，收件箱提示李薇确认 |
| wt_B（另一个刚建的单） | 已派工但还没开始（`started_at` 为空） | 退回 `pending`，正常重新派工 |

李薇看到 wt_A 的提示：

```
┌─ 需要你确认 ─────────────────────────────────────┐
│ 服务器重启时，这笔工作正在执行，无法确定是否已完成。│
│ 订单 ord-20261107-1155 的备注可能已经被修改过。    │
│                                                   │
│ [已完成，跳过] [重新执行]                          │
└───────────────────────────────────────────────────┘
```

> 为什么不能自动重跑：小巡可能已经改过订单备注了。盲目重跑会改两遍。
> 现状代码里 `requeue_expired` 是把所有过期投递无条件翻回 `failed` 再重试——
> 对"还没开始"的没问题，对"已经做到一半"的会重复执行外部动作。

## 7. 这一天的账

晚上李薇看了一眼「工作记录」的统计：

| 项 | 数量 |
|---|---|
| 收到事件 | 47 |
| 程序级过滤掉 | 31（采购单、物流通知、非销售类型） |
| 延后 | 6（夜间 2、额度用尽 1、时段外 3） |
| 限流跳过 | 2 |
| 进入研判 | 8 |
| 建的工单 | 5 |
| 其中需要她决定 | 1 |
| 她自己处理的事件 | 0 |

**她一天只被打扰了一次**——周女士那笔。

这是整个设计的落点。DeepSeek 的原话是「用尽量少的人的注意力，换尽量多的价值」。
反过来也成立：如果一个能替整个团队干活的东西，也能浪费整个团队的注意力，那它还不如没有。

## 8. 这个故事里每个机制对应的设计条目

| 故事里的时刻 | 机制 | 设计文档 |
|---|---|---|
| 23:40 夜间订单延后，次日取回 | `deferred` 语义 | §5.3 Gate 第 4 步 |
| 09:00 两条事件一次研判 | 批量研判 | §5.4 |
| 观察期只记录不执行 | `accept_mode = observe` | §5.5 |
| 工作记录不污染 DM 会话 | 会话隔离 | §5.11 |
| 10:05 建工单 | Ticket + Mandate | §5.1、§5.7 |
| 事件卡 + `work_read_event` | Inline & Spill | §5.10 |
| 10:12 提问、10:14 回答、恢复 | `attention` + `blocked` | §5.8、§5.13 |
| 14:20 付款事件直通 | Pass-through | §5.9 |
| 11:02 额度用尽延后 | Gate 第 5 步 | §5.3 |
| 11:15 限流留痕 | `skipped` | §5.3、B3 |
| 11:30 看板变化变成事件 | 数据回流 | §5.14、B-Phase 3 |
| 15:40 重启不重复执行 | `needs_review` | §5.12、B2 |
| 晚上只被打扰一次 | 注意力预算 | §5.13 Outbox |

## 9. 故事里没写、但实现时要回答的问题

| 问题 | 为什么重要 |
|---|---|
| 李薇怎么发现「工作记录」这个入口？ | B4 把主动工作移出 DM 后，如果面板上没有明确入口，用户会以为功能坏了 |
| 小巡在 work 会话里能看到它跟李薇的 DM 历史吗？ | 默认不能。如果需要跨会话记忆，要显式设计一条"只读引用"通道 |
| 同一个客户连续 4 单，会不会每次都建一个工单？ | 按 `stream_key`（订单维度）不会。但如果按客户维度聚合，需要另设 stream 规则 |
| 李薇手动点了「重新评估」一条 filtered 事件，会怎样？ | 需要定义：是绕过 Gate 直接进研判，还是重新走一遍 Gate？建议重新走，但记录"人工触发" |
| 小巡在 work 会话里的产出，怎么区分"只是草稿"和"已经执行了外部动作"？ | 关系到 wt_A 那种中断场景的判断。需要在 Report 里区分 `drafted` 和 `applied` |
