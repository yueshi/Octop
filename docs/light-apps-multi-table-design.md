# 轻应用多 CSV（多数据表）设计

> 状态：设计稿，未实施（2026-10-23）
>
> 范围：`feature/light-apps` 分支上的轻应用能力
>
> 关系：[轻应用数据与协作架构方案](./light-apps-architecture.md) 描述的是「行数据整体入库」的 P0 阶段；
> 本文是**先行的、可独立交付的增量**，两者不冲突：本文的表（table）维度在 P0 落地时映射为
> `light_app_rows.table_key`，服务层接口与前端契约不变。

---

## 1. 目标与范围

一个轻应用目前只有一张数据表（`schema.json` + `data.csv`）。本设计让**一个轻应用支持多个 CSV**：

- 每个应用下有若干**表**（table），每张表有自己的列定义和自己的 CSV 文件；
- Agent 可以在同一个应用里建多张表，并分别往不同表写数据；
- 应用界面（HTML）可以读取任意一张表，而不只是默认的那张。

**本次不做**

| 不做 | 原因 |
|------|------|
| 把行数据写进控制面 DB | 那是架构方案的 P0（13–17 人日）；本次保持 CSV 文件存储 |
| 删除表 / 删除列 | 删表等于删数据；若开放给 Agent 必须像 `app_delete` 一样强制 HITL，留到本轮跑通后单独加 |
| Dashboard 数据表编辑 UI | 架构方案 P0-4 的「只读数据表视图」另算；本次 Dashboard 只做参数透传与表清单展示 |
| MCP / CSV 导入等外部数据源 | 架构方案 P1；本设计只解决「应用内多表」 |

## 2. 概念模型

| 概念 | 说明 |
|------|------|
| 表（table） | 应用内的一张数据表：`key`（机器名）、`label`（展示名）、列定义、行 |
| 主表 | `key = "main"`。`app_create` 的 `columns` 生成主表，**永远**对应 `schema.json` + `data.csv` |
| 附加表 | 由 Agent 通过 `app_add_table` 创建，落在 `tables/<key>.schema.json` + `tables/<key>.csv` |

约束（`infra/apps/models.py`）：

- `key` 匹配 `^[A-Za-z_][A-Za-z0-9_]{0,63}$`；
- 保留字 `app` / `data` / `schema` / `manifest` / `tables` 不可用（防与文件名冲突）；
- 每个应用最多 12 张表；
- 每张表沿用现有上限：20 000 行 / 5 MB / 50 列 / 单元格 10 000 字符。

## 3. 存储布局

```
apps/<app_id>/
  app.html                    # UI（不变）
  manifest.json               # 扩展：表清单 + 每表 schema_version
  schema.json                 # 主表列定义（格式不变）
  data.csv                    # 主表行（不变）
  tables/orders.schema.json   # 附加表列定义
  tables/orders.csv           # 附加表行
```

**为什么主表留在根目录**：已部署实例里的既有应用数据就在根目录（`schema.json` + `data.csv`）。
留在原地意味着零迁移、零数据风险；代价只是 `key="main"` 在路径拼接上被特殊化一次
（`service.py` 内一个函数）。

**为什么列定义仍留在工作区**：Agent 可以直接 `read_file` 看到表的列，与今天 `schema.json`
的可见性一致。若把列定义搬进 DB，工作区只剩裸 CSV，Agent 自己读文件时看不到列结构。

**行存储保持文件形态**：追加仍是「读全量 → 校验 → 重写整个 CSV」，但**文件按表拆开**，
因此两个 Agent 并发写**不同表**不再互相覆盖；同表并发由现有的按应用 `asyncio.Lock`
串行化（`service.py` 的 `_lock_for`）。

## 4. 控制面：新增 `light_app_tables`

`light_apps` 已有 `row_count` / `html_bytes` / `data_bytes`。新增子表：

```sql
CREATE TABLE light_app_tables (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  table_id   TEXT NOT NULL UNIQUE,        -- 公开字符串 id
  app_id     TEXT NOT NULL REFERENCES light_apps(app_id) ON DELETE CASCADE,
  key        TEXT NOT NULL,                -- 机器名，app 内唯一
  label      TEXT NOT NULL DEFAULT '',
  row_count  INTEGER NOT NULL DEFAULT 0,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  UNIQUE(app_id, key)
);
```

PostgreSQL 版本把 `INTEGER PRIMARY KEY AUTOINCREMENT` 换成
`INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`，其余一致。

**为什么表清单放 DB**：应用列表页 `GET /api/apps` 现在几乎不做工作区读取
（`list_views_with_stats` 仅在缓存尺寸为 0 时才列目录，`service.py:268`）。若表清单靠列
`tables/` 目录推导，远程工作区（COS/S3）下每次列表都要打一次 LIST，列表页会退化。
DB 索引让列表保持零 I/O。

**repo 归属**：沿用 `LightAppRepo`（同一文件已承载 `light_app_collaborators` 这个子表），
不新增 RepoBundle 成员 → `services.py` / `manager.py` / 路由的 DI 不动。

**迁移编号**：v22 未随版本发布，按 `AGENTS.md` §7 的规则把新表**折进 `022_light_apps.sql`
与 `.pg.sql`**，`_schema_version` 仍为 22；在 `migrate.py` 的 `_ensure_light_apps_schema`
里补幂等 `CREATE TABLE IF NOT EXISTS`，覆盖已记录 v22 的本地库。

## 5. 读写与并发

| 操作 | 行为 |
|------|------|
| 读 | `read_rows(row, table_key)` 读该表 CSV，用该表 schema 校验表头（`parse_csv` 现有逻辑不变） |
| 写 | 读全量 → `validate_row` → `render_csv` → 重写该表 CSV |
| 并发 | 不同表互不覆盖；同表由按应用的 `asyncio.Lock` 串行化 |
| 原子写 | `_write_atomic` 的 pending 日志扩成支持应用内相对路径（`tables/x.csv`），暂存文件仍写 `<path>.new`；一组操作 = 该表的 (schema, data) 两个文件 |
| 计数 | 每表 `row_count` 记在 `light_app_tables`；`light_apps.row_count` = 各表之和（卡片显示总数），读取时按现有逻辑校正缓存 |
| 体积 | `light_apps.data_bytes` = 各表 CSV 体积之和；`html_bytes` 不变 |

删除应用时连带删除 `tables/` 目录；`app_delete` 的强制 HITL 逻辑不变。

## 6. 对外接口

### 6.1 Agent 工具（`infra/apps/tools.py`）

| 工具 | 变化 |
|------|------|
| `app_add_table(app_id, key, label, columns)` | **新增**。建表并落一份空 CSV。非破坏性，不进 HITL（与 `app_create` / `app_update_schema` 一致；只有 `app_delete` 强制审批） |
| `app_read_data(app_id, table, limit, offset)` | 增加可选 `table`，缺省 `main` |
| `app_append_row(app_id, row, table)` | 增加可选 `table`，缺省 `main` |
| `app_update_schema(app_id, columns, table)` | 增加可选 `table`，缺省 `main` |
| `app_list` | 每项带上该应用的表清单 |

所有新增 `table` 参数都是可选且缺省 `main` → 既有 prompt、既有生成的应用 HTML 无需修改。

配套改动：`infra/agents/settings/tool_catalog.py` 登记新工具；
`src/octop/i18n/{en,zh}.json` 增加工具显示名；专家模板
`infra/agents/experts/library/light-apps/AGENTS.md` 与全局 light-apps 提示词补充多表用法。

### 6.2 iframe SDK（`dashboard/src/pages/Apps/Detail.tsx` 的 `APP_SDK`）

```js
octopApp.schema(table?)                    // 该表列定义，缺省 main
octopApp.listRows({table, limit, offset})  // 读该表
octopApp.appendRow(row, {table})           // 追加到该表
octopApp.tables()                          // 表清单，供页面渲染切换器
```

### 6.3 HTTP API（`api/routers/apps.py`）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/apps/{id}/tables` | 表清单（key、label、列定义、行数） |
| GET | `/api/apps/{id}/rows?table=main&limit&offset` | 读指定表 |
| POST | `/api/apps/{id}/rows` | body `{row, table?}`，追加到指定表 |

### 6.4 Dashboard

本期只做透传：SDK → 宿主 → API 带上 `table`；信息抽屉里展示表清单。数据表编辑 UI 不在本次范围。

## 7. 兼容与迁移

| 场景 | 处理 |
|------|------|
| 既有应用没有 `light_app_tables` 行 | 读路径回退：视作只有主表 `main`（列来自 `schema.json`，行来自 `data.csv`） |
| 既有应用被写入 | 首次写入时补一条 `light_app_tables` 行（key=`main`） |
| 既有应用的工作区文件 | 原样保留，不需要迁移脚本 |
| 既有生成的 HTML / prompt | `table` 参数可选且缺省 `main`，行为不变 |
| `app_delete` | 连带删除 `tables/` 目录；强制 HITL 不变 |

## 8. 实施顺序

1. **模型与存储**
   - `infra/apps/models.py`：`MAIN_TABLE_KEY`、`TABLE_KEY_RE`、`RESERVED_TABLE_KEYS`、`MAX_TABLES_PER_APP`、`TableSpec`；
   - `infra/db/migrations/022_light_apps.sql` + `.pg.sql`：新表；`migrate.py` 幂等补齐；
   - `infra/db/repos/apps.py`：`LightAppRepo` 增加表清单方法。
2. **服务层**
   - `infra/apps/service.py`：按表读写、建表、删表目录、计数与体积统计。
3. **Agent 接口**
   - `infra/apps/tools.py`：`app_add_table` + 三个工具加 `table` 参数；
   - `infra/agents/settings/tool_catalog.py` 登记；`i18n/{en,zh}.json` 加工具名；
   - 专家模板与全局提示词补充多表用法。
4. **HTTP 与前端**
   - `api/routers/apps.py`：`/tables` 端点、rows 支持 `table`；
   - `dashboard`：`Detail.tsx` 的 SDK 与宿主转发、`api/modules/apps.ts`。
5. **测试与收尾**
   - 单测：models / service / tools；
   - 集成测试：`/tables`、带 `table` 的 rows 读写；
   - 更新既有断言（例如「文件清单恰好 4 个」）；
   - `make all`。

## 9. 与架构方案 P0 的衔接

P0 落地时：

| 本设计 | P0 之后 |
|---------|---------|
| `light_app_tables`（key、label、行数） | 保留，作为表的元数据索引 |
| 表的列定义在工作区文件 | 移入 `light_app_rows` 所在的应用 schema（`light_apps.schema_json` 扩展为按表） |
| 表的行在工作区 CSV | 移入 `light_app_rows`，新增 `table_key` 列 |
| `read_rows(row, table_key)` 等服务层签名 | 不变，只换存储实现 |

前端与 Agent 工具的契约（`table` 参数、SDK 方法）保持不变，因此本设计可以先行交付，
P0 落地时不需要再改调用方。
